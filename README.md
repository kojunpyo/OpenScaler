# OpenScaler

[![Build](https://github.com/kojunpyo/OpenScaler/actions/workflows/build.yml/badge.svg)](https://github.com/kojunpyo/OpenScaler/actions/workflows/build.yml)
[![Release](https://img.shields.io/github/v/release/kojunpyo/OpenScaler)](https://github.com/kojunpyo/OpenScaler/releases/latest)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

**창 모드 게임을 실시간으로 캡처해, 더 선명하게 키우고 더 부드럽게 보여 주는 오픈소스 Windows 프로그램**

게임을 고치지 않고 화면만 보고 동작하므로 어떤 게임에도 쓸 수 있습니다. 상용 프로그램 [Lossless Scaling](https://store.steampowered.com/app/993090/Lossless_Scaling/)의 핵심 기능인 업스케일링과 프레임 생성을 오픈소스로 직접 구현했습니다.

여기에 더해, OpenScaler는 **쓸수록 그 게임에 맞춰집니다.** 게임을 하는 동안 만든 프레임을 스스로 채점하고, 점수가 오르는 쪽으로 게임마다 설정을 고쳐 나갑니다 ([게임별 학습](#5-게임별-학습)). 화면은 저장하지 않으며, 게임마다 35KB 이하의 파일 하나만 남깁니다.

![시연: 왼쪽은 일반 확대, 오른쪽은 OpenScaler](docs/demo.webp)

> 30fps 영상을 640×360 창에서 2560×1440으로 확대. 왼쪽 일반 확대 30fps, 오른쪽 OpenScaler(FSR 1.0 + RIFE) 60fps, 실제 속도. 영상: [Why is NieR: Automata's combat so satisfying?](https://www.youtube.com/watch?v=z6La_S9YoJ4) (Shen One)

## 1. 왜 필요한가

### 1.1 낮은 해상도로 돌리면 화면이 흐려진다

게임이 버거울 때 프레임을 올리는 가장 확실한 방법은 해상도를 낮추는 것입니다. 1920×1080 대신 1280×720으로 돌리면 그릴 픽셀이 절반 아래로 줄어듭니다. 하지만 그 화면을 모니터에 꽉 채우면 모니터나 그래픽 드라이버가 주변 픽셀을 단순히 섞어 늘리므로 글자와 윤곽선이 뿌옇게 번지고, 창 모드로 두면 화면 가운데에 작은 창으로 남습니다. 성능이 충분해도 같은 문제가 생기는 경우가 있습니다.

- **해상도가 고정된 게임**: 오래된 게임, 인디 게임, 에뮬레이터는 640×480이나 1280×720만 지원하기도 합니다.
- **픽셀 아트 게임**: 섞어서 늘리면 각진 그림이 뭉개집니다. 정확히 2배, 3배로 키워야 원래 모양이 유지됩니다.
- **고해상도 모니터**: 1440p나 4K 모니터에서는 더 많이 늘려야 해서 더 흐려집니다.

### 1.2 프레임이 낮으면 고주사율 모니터가 소용없다

144Hz나 240Hz 모니터도 게임이 30fps나 60fps로만 나오면 그만큼만 부드럽습니다. 게임이 실제로 그린 프레임(이 문서에서는 "게임 프레임") 사이에 새 프레임을 넣는 "프레임 생성"이 해결책이지만, NVIDIA DLSS 프레임 생성이나 AMD FSR 3는 게임 개발사가 직접 넣어 줘야 하고, DLSS 프레임 생성은 최신 NVIDIA 그래픽카드에서만 동작합니다.

### 1.3 게임마다 맞는 설정이 다르다

화면만 보고 프레임을 만들려면 앞뒤 프레임에서 무엇이 어디로 움직였는지 추측해야 하는데, 잘 맞는 값(움직임을 찾는 칸의 크기, 찾는 범위, 주변과 다른 움직임을 얼마나 믿을지)이 게임마다 다릅니다. 리듬게임은 생김새가 같은 노트가 빠르게 내려와 서로 헷갈리기 쉽고, 횡스크롤 게임은 화면 전체가 흘러 넓게 찾아야 하며, 체력 바나 점수처럼 고정된 글자 위로 물체가 지나가는 게임도 있습니다. 사용자가 이런 값을 직접 맞추고 맞았는지 확인하기는 어렵습니다.

### 1.4 그래서 게임 밖에서 처리하고, 게임에 맞춰 스스로 조정한다

OpenScaler는 게임과 상관없이 **화면만 보고** 처리합니다. 게임을 낮은 해상도의 창 모드로 실행하면 그 창을 실시간으로 캡처해 윤곽선을 살리는 알고리즘으로 모니터 크기까지 키우고, 원하면 게임 프레임 사이에 움직임을 맞춘 프레임을 넣어 주사율까지 채웁니다. 결과는 전체화면으로 덮어 보여 주고 마우스 클릭은 그대로 게임에 전달합니다. 게임을 하는 동안에는 만든 프레임을 정답과 비교해 채점하며 그 게임에 맞는 설정을 찾아 기억합니다.

같은 일을 하는 Lossless Scaling은 유료이고 소스가 공개되어 있지 않으며, 오픈소스인 [Magpie](https://github.com/Blinue/Magpie)는 업스케일링에 집중합니다. OpenScaler는 업스케일링과 프레임 생성을 함께 오픈소스로 구현하고 게임별 학습을 더했습니다. 또 각 단계(화면 캡처, GPU 셰이더, 움직임 추정, 신경망 실행, 입력 처리)가 어떻게 동작하는지 코드로 보여 주는 것을 목표로 합니다.

| | 화면 확대 | 프레임 생성 | 게임 지원 필요 | 게임에 맞춰 스스로 조정 | 그래픽카드 | 소스 공개 |
|---|---|---|---|---|---|---|
| 모니터, 드라이버의 기본 확대 | 단순 섞기 (흐림) | 없음 | 아니요 | - | 모두 | - |
| DLSS, FSR 3 (게임 내장) | 있음 | 있음 | **예** | 해당 없음 (게임이 움직임 정보를 줌) | 제품마다 다름 | 일부 |
| Lossless Scaling | 있음 | 있음 | 아니요 | 아니요 (설정은 사용자가 고름) | 모두 | 아니요 (유료) |
| **OpenScaler** | 있음 | 있음 | 아니요 | **예 (게임별 학습)** | Direct3D 11 GPU | **예 (MIT)** |

## 2. 핵심 기능

- **선명한 업스케일**: 게임 창을 모니터 크기로 키웁니다. 기본값인 AMD FSR 1.0은 윤곽선의 방향을 보고 보간해 글자와 테두리가 번지지 않습니다.
- **프레임 생성**: 게임 프레임 사이(보간)나 다음 게임 프레임 전(외삽)에 움직임을 맞춘 프레임을 넣어, 30fps 게임도 모니터 주사율만큼 부드럽게 보여 줍니다.
- **게임별 학습**: 게임마다 생성 결과를 스스로 채점하며 설정을 맞추고, 화면에서 자주 움직이는 곳을 기억합니다. 쓸수록 그 게임에 맞춰집니다. 화면은 저장하지 않습니다 ([자세히](#5-게임별-학습)).
- **그대로 쓰는 마우스**: 확대된 화면에서 클릭한 곳이 원래 게임 창의 같은 위치로 들어갑니다.

## 3. 설치와 사용법

### 3.1 다운로드

[Releases](https://github.com/kojunpyo/OpenScaler/releases/latest)에서 `OpenScaler-windows-x64.zip`을 받아 압축을 풀면 됩니다. 설치는 필요 없습니다.

필요한 환경: Windows 10 1903 이상 또는 Windows 11, Direct3D 11을 지원하는 그래픽카드

### 3.2 사용법

1. 게임을 **창 모드**로, 모니터보다 낮은 해상도(예: 1280×720)로 실행합니다.
2. `OpenScaler.exe`를 실행하면 설정 창이 열립니다.
3. **대상 창** 목록에서 게임을 고르고 **확대 시작**을 누릅니다. 게임 창을 클릭한 뒤 **Alt+Shift+S**를 눌러도 됩니다.
4. 확대 화면 오른쪽에 메뉴가 열리고, 가운데에 "프레임 생성 영역을 지정할까요?"를 묻습니다 (아래 설명). 그냥 쓰려면 **아니오**를 누릅니다.
5. 멈출 때는 **Alt+Shift+S**를 누릅니다. 설정 창을 닫으면 프로그램이 종료됩니다.

**확대 화면 위 메뉴**: 확대 화면이 설정 창을 덮어도, 메뉴(**Alt+Shift+G**로 열고 닫음)에서 설정 창과 같은 설정(업스케일, 프레임 생성, 영역 지정과 추천, 슬로모션, 게임별 학습, 화면 표시)을 마우스로 바꿀 수 있어 모니터가 하나여도 됩니다. 메뉴를 눌러도 게임 창의 포커스는 그대로라 게임이 멈추지 않습니다. 1인칭 게임처럼 커서를 창 가운데 붙잡아 두는 게임은 게임의 메뉴(Esc)를 먼저 열어야 메뉴를 누를 수 있습니다. 학습 데이터 내보내기와 가져오기는 파일 창이 확대 화면 뒤로 숨으므로 설정 창에서만 합니다.

**프레임 생성 영역 지정**: 팝업에서 **예**를 누르면 메뉴가 숨고 위쪽에 "추천 영역 계산 중..."이 뜹니다. 10초쯤 게임을 계속하면 자주 움직인 곳을 감싼 영역이 편집 창에 그려지고, 테두리를 다듬어 Enter로 저장합니다 (Esc는 취소, 계산 중 취소는 Alt+Shift+G). 화면 대부분이 움직이는 게임이면 직접 지정할지 묻습니다. 프레임 생성이 꺼져 있었다면 **예**를 누를 때 켭니다. 프레임 생성은 메뉴, 설정 창, **Alt+Shift+F**로도 켜고 끕니다.

### 3.4 슬로모션 테스트

고주사율 모니터가 없어도 만든 프레임을 볼 수 있게, 1초쯤 녹화해 120Hz만큼 채운 뒤 느리게 재생합니다. 확대 중 Alt+Shift+T로 시작하고 끝냅니다. 재생 중에는 Alt+Shift+Space로 멈추고 Alt+Shift+←/→로 한 장씩 넘깁니다. 실제 지연과 끊김은 이 테스트로 알 수 없습니다.

### 3.5 RIFE 엔진

릴리스 zip에는 RIFE 엔진에 필요한 `rife` 폴더(약 57MB)가 들어 있어, 압축을 풀고 설정 창의 **방식**에서 **RIFE 보간**을 고르면 바로 쓸 수 있습니다. 처음 고르면 신경망을 준비하느라 몇 초 걸리고, 그동안은 블록 매칭을 씁니다. `rife` 폴더를 지우면 블록 매칭만 씁니다.

신경망은 Windows의 DirectML로 돌리므로 그래픽카드 제조사에 묶이지 않습니다. 그래픽카드가 둘인 노트북에서는 성능이 높은 쪽을 고릅니다.

### 3.6 설정 파일

바꾼 설정은 실행 파일 옆의 `OpenScaler.ini`에 자동으로 저장되고 다음 실행 때 그대로 불러옵니다. 비교 모드는 확인용이라 저장하지 않습니다.

```ini
[Settings]
Mode=fsr              ; nearest, bilinear, bicubic, lanczos2, fsr
Sharpness=0.5         ; 0.0 ~ 1.0
IntegerScale=0        ; 1이면 정수배 스케일링
AlwaysShowStatus=0    ; 1이면 화면 위 상태 표시를 항상 켬
AdjustCursorSpeed=0   ; 1이면 커서 속도 보정
FrameGen=0            ; 1이면 프레임 생성
FgMethod=0            ; 0: 보간, 1: 외삽 (설정 창의 방식이 외삽이면 1)
FgGenerator=0         ; 0: 블록 매칭 (기본값), 1: RIFE
FgQuality=1           ; 정밀도. 0: 낮음, 1: 기본, 2: 높음
FgPreset=0            ; 화면 지도. 0: 자동, 1: 끔
```

게임별 학습 기록은 실행 파일 옆 `profiles` 폴더에 게임마다 저장됩니다 ([학습 데이터 관리](#53-학습-데이터-관리)).

### 3.7 문제 해결

| 증상 | 해결 |
|---|---|
| 게임 화면이 캡처되지 않습니다 | 전용 전체화면(Exclusive Fullscreen)은 캡처할 수 없습니다. 게임을 창 모드로 실행하세요 |
| 144Hz 모니터인데 확대 화면이 초당 60장으로 나옵니다 | Windows 10은 주 모니터의 주사율로 화면을 합성합니다. 고주사율 모니터를 주 모니터로 두세요 |
| 고주사율에서 화면이 가끔 끊깁니다 | NVIDIA 제어판 → 3D 설정 관리 → 프로그램 설정에서 OpenScaler의 전원 관리 모드를 "최대 성능 선호"로 바꾸세요. 그래도 끊기면 프레임 생성 영역을 움직이는 부분만 지정합니다 (**영역 추천**) |
| 같은 장면이 두 번씩 나와 덜컥거립니다 | 배수를 **자동**으로 두세요. 2배, 3배로 고정하면 주사율을 게임 fps로 고르게 나누지 못할 때가 있습니다 |
| 프레임 생성을 켜도 부드러워지지 않습니다 | 게임 fps가 주사율의 87% 이상이면 넣을 자리가 없어 프레임 생성이 쉽니다. Alt+Shift+O로 상태 표시를 켜서 게임 fps를 확인하세요 |
| RIFE 보간이 동작하지 않습니다 | 릴리스 zip의 `rife` 폴더가 `OpenScaler.exe` 옆에 있어야 합니다. 처음 고르면 신경망을 준비하는 몇 초 동안은 블록 매칭을 씁니다 |
| 확대 화면에서 커서가 너무 빠릅니다 | 커서 속도 보정(Alt+Shift+P)을 켜세요 |
| 비정상 종료 뒤 마우스 속도가 바뀌어 있습니다 | OpenScaler를 다시 실행하면 원래 속도로 되돌립니다 |
| 클릭이 다른 창으로 갑니다 | 게임 창과 확대 화면 사이에 다른 창이 겹치지 않게 하세요 |
| 확대 화면 위 메뉴를 누를 수 없습니다 | 커서를 붙잡아 두는 게임(1인칭 게임 등)은 게임의 메뉴(Esc)를 열어 커서를 풀어 주세요 |
| 게임 창 둘레에 노란 테두리가 보입니다 | Windows 10이 캡처 중인 창에 그리는 표시이며 동작에는 영향이 없습니다 (Windows 11에서는 숨김) |

### 4.2 프레임 생성

| 기능 | 설명 |
|---|---|
| 방식: 블록 매칭 보간 (기본값) | 화면을 작은 칸으로 나눠 앞뒤 게임 프레임에서 같은 모양을 찾고, 두 프레임 사이에 중간 프레임을 만듭니다. [게임별 학습](#5-게임별-학습)이 게임마다 값을 맞추므로 쓸수록 그 게임에 맞춰집니다. 화면이 게임 프레임 한 장만큼 늦어집니다 |
| 방식: RIFE 보간 | 신경망([RIFE](https://github.com/hzwer/Practical-RIFE))으로 움직임을 찾아 중간 프레임을 만듭니다. 빠른 움직임과 밝기 변화에 강하지만 GPU를 더 쓰고, 신경망 시간만큼 더 늦어집니다. 게임별 학습은 적용되지 않습니다 ([RIFE 엔진](#35-rife-엔진)) |
| 방식: 블록 매칭 외삽 (실험) | 지금까지의 움직임으로 다음 게임 프레임이 오기 전 장면을 미리 만듭니다. 화면이 늦어지지 않지만 덜 정확합니다 |
| 배수 | 주사율까지 자동으로 채우거나 2배, 3배, 4배로 고정합니다 |
| 정밀도 | 움직임을 찾는 영상의 해상도를 낮음, 기본, 높음 중에서 고릅니다. RIFE가 제때 끝나지 못하면 해상도를 자동으로 낮춥니다 |
| 게임별 학습과 화면 지도 | 만든 프레임을 스스로 채점해 게임마다 설정을 맞추고, 자주 움직이는 곳과 방향을 기억합니다 ([게임별 학습](#5-게임별-학습)) |
| 프레임 생성 영역 | 리듬게임의 건반처럼 움직이는 곳만 골라 그 안에서만 프레임을 만들고 학습합니다. 확대 중 **영역 지정하기**를 누르면 확대 화면 위에 사각형이 뜨고, 테두리를 끌어 크기를, 안쪽을 끌어 위치를 정한 뒤 Enter로 저장합니다. 게임마다 따로 기억하고, 영역 밖은 게임 화면을 그대로 보여 줍니다. DJMAX 720p에서 가운데 절반만 지정하면 움직임 찾기는 66%, 합성은 59%의 시간으로 줄었습니다 (GTX 1060) |
| 영역 추천 | 프레임 생성을 켜고 10초쯤 플레이한 뒤 **영역 추천**을 누르면, 최근 10초 동안 자주 바뀐 곳을 감싼 사각형을 영역 편집 창에 그려 줍니다. 다듬어서 Enter로 저장합니다. DJMAX에서는 건반과 판정선을 찾았고(배경 영상은 은은하게 바뀌어 빠짐), 시점이 움직이는 마인크래프트에서는 "화면 대부분이 움직여서 좁힐 곳이 없어요"라고 알려 줍니다 |
| 움직임 시각화 | 찾아낸 움직임을 색(방향)과 진하기(빠르기)로 보여 줍니다 (블록 매칭, 외삽) |

방식은 세 가지 중에서 고릅니다. 대부분은 기본값인 블록 매칭 보간을 그대로 쓰면 되고, 빠른 움직임에서 화면이 자주 깨지면 RIFE 보간, 화면이 늦어지는 것이 싫으면 블록 매칭 외삽을 고릅니다. "보간"과 "외삽"은 프레임을 어디에 만드는지(두 게임 프레임 사이인지, 최근 프레임 다음인지), "블록 매칭"과 "RIFE"는 움직임을 어떻게 찾는지를 뜻합니다. 어떤 방식이 어느 정도의 결과를 내는지는 [성능 평가 기준](#6-성능-평가-기준)에 있습니다.

## 5. 게임별 학습

OpenScaler는 프레임 생성을 켜고 게임을 확대하는 동안 스스로 결과를 채점하고, 그 게임에 더 맞는 설정을 찾아 기억합니다. 다음에 같은 게임을 확대하면 학습한 설정으로 바로 시작합니다.

### 5.1 어떻게 배우나

정답이 있어야 채점할 수 있는데, 화면만 보는 프로그램에는 "생성한 프레임의 정답"이 없습니다. 그래서 정답을 아는 상황을 만들어 시험합니다.

1. **문제 내기**: 1초에 한 번, 이어진 게임 프레임 세 장(A, B, C) 중 가운데 B를 가립니다.
2. **풀기**: A와 C만 보고 B 자리의 프레임을 만듭니다. 지금 설정과 시험할 후보 설정으로 한 번씩 만듭니다.
3. **채점**: 만든 프레임을 진짜 B와 비교해 점수(PSNR, dB)를 매깁니다. 계산은 모두 GPU에서 하고 화면은 바로 버립니다.
4. **고치기**: 후보를 6번 시험해 평균이 0.05dB 넘게 좋으면 채택합니다. 다섯 가지 값을 하나씩 돌아가며 후보를 바꿉니다.
5. **되돌아보기**: 메뉴나 결과 화면에서 고른 값이 게임 화면에서는 나쁠 수 있으므로, 세 번에 한 번은 기본값을 후보로 다시 시험해 더 나으면 되돌립니다.

**외삽은 따로 배웁니다.** 외삽은 다음 게임 프레임을 보지 않고 미리 만들기 때문에, 잘 맞는 값이 보간과 다릅니다. 그래서 블록 매칭 외삽을 쓰는 동안에는 문제를 이렇게 바꿉니다.

1. **문제 내기**: 이어진 게임 프레임 세 장(A, B, C) 중 마지막 C를 가립니다.
2. **풀기**: A와 B만 보고 C가 올 시각의 장면을 예측합니다. 실제 외삽과 같은 방법입니다.
3. **채점**: 예측한 장면을 진짜 C와 비교합니다. 기준은 "B를 그대로 보여 줬을 때"(프레임 생성이 없을 때)입니다.

고치기와 되돌아보기는 보간과 같고, 학습한 값은 보간용과 외삽용을 따로 저장합니다.

함께 **화면 지도**도 쌓습니다. 화면을 32×18칸으로 나눠, 칸마다 자주 움직이는지, 주로 어느 방향으로 움직이는지를 평균 냅니다. 리듬게임이라면 노트가 내려오는 줄, 고정된 UI 자리가 드러납니다. 지도는 채점에서 더 좋게 나올 때만 움직임 찾기의 후보로 씁니다.

| 학습하는 값 | 뜻 | 기본값 |
|---|---|---|
| 칸 크기 | 움직임을 몇 픽셀 단위로 찾을지. 작을수록 작은 물체를 따라가고, 클수록 덜 흔들림 | 4픽셀 |
| 찾는 범위 | 한 프레임 사이에 얼마나 멀리 움직인 것까지 찾을지 | 12 |
| 벌점 | 주변과 다른 움직임을 얼마나 의심할지 | 0.0015 |
| 허용 밝기 차이 | 앞뒤 프레임을 합칠 때 어느 정도 다른 픽셀까지 섞을지 | 0.08 |
| 화면 지도 | 지도를 움직임 찾기에 쓸지 | 안 씀 |

설정 창의 **게임별 학습** 구역에서 게임마다 보간과 외삽 각각의 채점 횟수, 설정을 바꾼 횟수, 기본값과 다른 값의 개수를 볼 수 있습니다. 점수 그래프는 지금 고른 방식의 것을 보여 줍니다 (보간은 두 장을 단순히 섞은 결과, 외삽은 앞 프레임을 그대로 둔 결과와 함께).

### 5.2 효과

같은 영상의 앞 절반으로 학습하고, 학습에 쓰지 않은 뒤 절반에서 기본값과 비교했습니다 (GTX 1060).

| 영상 | 학습 전 → 학습 후 |
|---|---|
| 계산으로 만든 장면 6가지 (화면 이동, 고정 UI, 작은 물체, 리듬게임 노트, 빠른 이동, 밝기 변화) | 장면마다 +1.3 ~ +13.2dB |
| DJMAX RESPECT V 플레이 녹화 3개, 다른 화면이 섞인 경우까지 21가지 | 평균 +0.34dB, 가장 나쁜 경우 -0.60dB (21가지 중 1번 나빠짐) |
| 마인크래프트 Java판 시점 회전 녹화 1개, 다른 화면이 섞인 경우까지 7가지 | 7가지 모두 좋아짐, +0.09 ~ +1.60dB |
| 외삽: DJMAX 녹화 3개 × 7가지 (30fps 게임을 외삽하는 간격) | 21가지 모두 좋아짐, 평균 +2.06dB (+0.02 ~ +3.46dB) |
| 외삽: 마인크래프트 녹화 1개 × 7가지 | 7가지 모두 좋아짐, +0.03 ~ +0.44dB |

- 학습은 블록 매칭 보간(기본값)과 블록 매칭 외삽의 값을 각각 바꿉니다. RIFE 보간은 미리 학습된 신경망을 그대로 쓰므로, RIFE를 고르면 채점과 화면 지도는 쌓이지만 RIFE의 결과는 바뀌지 않습니다.
- DJMAX에서 외삽의 기본값은 프레임 생성이 없을 때의 오차 중 53%를 없앴고, 학습 후에는 77%를 없앴습니다 (첫 녹화, 다른 화면이 섞이지 않은 경우).
- 실제 게임을 오래 하면서 체감이 좋아지는지는 아직 확인하지 못했습니다.

### 5.3 학습 데이터 관리

- **화면은 저장하지 않습니다.** 채점에 쓴 프레임은 GPU 메모리에서 바로 버리고, 디스크에는 숫자로 된 결과만 남깁니다. 인터넷으로 보내는 것도 없습니다.
- **게임마다 파일 하나**: 실행 파일 옆 `profiles` 폴더에 `게임 실행 파일 이름.json`으로 저장합니다. 마인크래프트 Java판의 `javaw`처럼 여러 게임이 함께 쓰는 실행 파일이면 창 제목에서 버전 번호와 뒤쪽 상태 표시를 뺀 이름을 붙여 `Minecraft (javaw).json`처럼 구분합니다. 보간용과 외삽용 학습값(각 다섯 개), 화면 지도, 점수 기록, 채점 횟수가 들어 있습니다.
- **크기가 정해져 있습니다**: 화면 지도는 칸 수가 고정이고, 점수 기록은 보간과 외삽 각각 채점 20번마다 한 점씩 최근 240점까지만 남깁니다. 저장할 때마다 파일을 새로 덮어쓰므로 오래 써도 커지지 않습니다. 오래 학습한 게임도 파일 하나가 26KB 정도이고, 점수 기록이 가득 차도 35KB를 넘지 않아 게임 100개를 학습해도 3.5MB 이하입니다.
- **저장 시점**: 확대 중 1분마다, 그리고 확대를 멈출 때 저장합니다. 프로그램이 갑자기 꺼져도 최근 1분 안쪽의 학습만 잃습니다.
- **지우기와 끄기**: 설정 창의 게임별 학습 구역에서 게임을 고르고 **이 게임 기록 지우기**를 누르면 그 파일을 지웁니다. `profiles` 폴더를 통째로 지워도 됩니다. **게임별 학습 켜기**를 끄면 채점도 하지 않습니다.

### 5.4 학습 데이터 공유

잘 학습된 데이터는 **공유용으로 내보내기**로 파일을 만들어 다른 사람에게 줄 수 있고, 받은 사람은 **공유 데이터 가져오기**로 넣어 그 상태에서 이어서 학습합니다. 더 좋아지면 다시 공유합니다. 게임마다 가장 좋은 데이터는 [`shared-profiles`](shared-profiles) 폴더에 모읍니다.

- **내보내기**: 설정 창 **게임별 학습** 구역에서 게임을 고르고 **공유용으로 내보내기**를 누릅니다. 파일 이름(`게임 이름.json`)은 바꾸지 않는 것이 좋습니다.
- **가져오기**: `shared-profiles`에서 파일을 받아 **공유 데이터 가져오기**로 고릅니다. 이미 그 게임의 데이터가 있으면 `profiles\backup` 폴더로 옮겨 두므로 되돌릴 수 있습니다.
- **언제 공유하나**: 설정 창의 "최근 채점 200회 평균, 기준보다 +dB"가 공유의 기준입니다. 기준은 보간이면 앞뒤 프레임을 단순히 섞은 것, 외삽이면 앞 프레임을 그대로 둔 것입니다. 채점이 200회(프레임 생성을 켜고 3~4분) 넘게 쌓인 뒤가 좋습니다.
- 파일에는 학습값, 화면 지도, 점수 기록, 프레임 생성 영역만 들어 있고 화면, 컴퓨터 이름, 경로는 없습니다. 저장소에 올리는 방법은 [9.4 학습 데이터 올리기](#94-학습-데이터-올리기)에 있습니다.

## 6. 성능 평가 기준

"프레임 생성이 잘 된다"는 말만으로는 어느 정도인지 알 수 없습니다. OpenScaler는 생성한 프레임의 **화질**과 실시간 **부드러움, 지연**을 아래 기준으로 숫자를 매깁니다. 측정 도구가 같은 기준으로 등급을 출력합니다 (`tools/test/fgquality.py`, `tools/test/fgtiming.py`).

### 6.1 화질: 프레임 생성이 없을 때의 오차를 얼마나 없앴나

정답을 아는 상황을 만들어 비교합니다. 60fps로 녹화한 게임 프레임에서 하나 건너 하나를 빼면 30fps 게임과 같아지고, 뺀 프레임이 정답이 됩니다. 정답 자리에 무엇을 보여 주느냐에 따라 오차가 달라집니다.

- **멈춤 (생성 없음)**: 앞 프레임을 그대로 보여 줍니다. 프레임 생성을 끈 화면과 같습니다. 이 오차가 기준(0%)입니다.
- **단순 섞기**: 앞뒤 프레임을 반씩 섞습니다. 가장 값싼 방법이라, 이보다 확실히 나아야 의미가 있습니다.
- **OpenScaler**: 움직임을 찾아 만든 프레임입니다.

**오차 감소율** = 멈춤의 오차(평균 제곱 오차) 중 몇 %를 없앴는가. 100%면 정답과 같습니다.

| 등급 | 오차 감소율 | 화면에서 보이는 모습 |
|---|---|---|
| 좋음 | 85% 이상 | 움직이는 물체가 제자리에 있고, 깨짐은 멈춰 놓고 찾아야 보입니다 |
| 보통 | 65 ~ 85% | 대부분 맞지만 고정된 글자나 조준점 위, 빠른 물체 가장자리에 흔적이 남습니다 |
| 아쉬움 | 40 ~ 65% | 단순 섞기보다는 낫지만 잔상이나 블록 모양 깨짐이 자주 보입니다 |
| 나쁨 | 40% 미만 | 단순 섞기(보통 30~40%) 수준입니다 |

dB(PSNR)도 함께 적습니다. 숫자가 감이 오지 않으면 픽셀 하나가 정답과 평균 몇 단계(0~255) 다른지로 읽으면 됩니다.

| PSNR | 20dB | 25dB | 30dB | 35dB | 40dB |
|---|---|---|---|---|---|
| 평균 픽셀 오차 | 25.5단계 (10%) | 14.3단계 (5.6%) | 8.1단계 (3.2%) | 4.5단계 (1.8%) | 2.6단계 (1.0%) |

나뭇잎처럼 잔무늬가 많은 화면은 조금만 어긋나도 오차가 크게 나와 dB만으로는 게임끼리 비교하기 어렵습니다. 그래서 등급은 같은 화면의 "멈춤"과 비교한 오차 감소율로 매깁니다.

지금까지 잰 결과 (30fps 게임을 60fps로 채우는 간격, GTX 1060):

| 게임 | 멈춤 | 단순 섞기 | 블록 매칭 | RIFE |
|---|---|---|---|---|
| DJMAX RESPECT V (리듬게임, 1280×720) | 20.6dB | 22.7dB, 38% 나쁨 | 29.6dB, 87% **좋음** | 30.5dB, 90% **좋음** |
| 마인크래프트 (시점 회전, 854×480) | 18.8dB | 20.3dB, 29% 나쁨 | 22.9dB, 61% 아쉬움 | 25.0dB, 76% **보통** |

게임이 더 느리면 프레임 사이 간격이 벌어져 등급이 내려갑니다. 15fps 게임과 같은 간격에서는 블록 매칭 59~73%, RIFE 75~81%였습니다 (마인크래프트, DJMAX).

### 6.2 실시간: 부드러운가, 늦지 않은가

실제로 게임을 확대하며 화면마다 기록한 로그(`--fg-log`)로 잽니다. "칸"은 모니터가 화면을 한 번 그리는 시간입니다 (60Hz면 16.7ms, 144Hz면 6.9ms). 그래서 주사율이 달라도 같은 기준을 씁니다.

| 항목 | 뜻 | 좋음 | 보통 |
|---|---|---|---|
| 출력 fps / 주사율 | 모니터가 그릴 때마다 새 화면을 냈는가 | 98% 이상 | 90% 이상 |
| 출력 끊김 | 화면이 1.5칸 넘게 늦게 나온 횟수 | 분당 1번 이하 | 분당 6번 이하 |
| 화면 속 시간 고르기 | 화면마다 게임 속 시간이 고르게 흐르는가 (흔들림의 표준편차) | 0.25칸 이하 | 0.5칸 이하 |
| 멈춤 | 같은 장면이 두 번 나온 비율 | 1% 이하 | 5% 이하 |
| 건너뜀 | 게임 속 시간이 2칸 넘게 한꺼번에 흐른 횟수 | 분당 1번 이하 | 분당 6번 이하 |
| 추가 지연 | 보간이 원래 늦추는 게임 프레임 한 장 외에 더 늦어진 시간 | 10ms 이하 | 25ms 이하 |
| RIFE를 제때 쓴 비율 | 신경망 결과가 늦어 블록 매칭으로 대신하지 않은 비율 | 95% 이상 | 80% 이상 |

지금까지 잰 결과 (60Hz 모니터, GTX 1060):

| 경우 | 출력 | 끊김 | 시간 고르기 | 멈춤 | 건너뜀 | 추가 지연 | RIFE 제때 |
|---|---|---|---|---|---|---|---|
| 마인크래프트 30fps, 블록 매칭 보간 | 100% 좋음 | 분당 2.9번 보통 | 0.09칸 좋음 | 0% 좋음 | 분당 0번 좋음 | 1.9ms 좋음 | - |
| 마인크래프트 30fps, 블록 매칭 외삽 | 100% 좋음 | 분당 2.9번 보통 | 0.07칸 좋음 | 0% 좋음 | 분당 0번 좋음 | 0ms (늦추지 않음) | - |
| 데모 창 21fps, RIFE 보간 | 98% 좋음 | 분당 0번 좋음 | 0.29칸 보통 | 0% 좋음 | 분당 0번 좋음 | 44.1ms 나쁨 | 100% 좋음 |

- 마인크래프트는 게임의 최대 프레임률을 30으로 낮추고 시점을 계속 돌리며 30초씩 잰 값입니다 (`tools/test/devicecheck.ps1`).
- RIFE는 신경망 결과를 기다리느라 화면을 놓치지 않도록, 결과가 나오기까지 걸린 시간만큼 화면을 늦춰 보여 줍니다. 그래서 끊김과 건너뜀은 없지만 추가 지연이 큽니다. 데모 창 값은 세 번 잰 중앙값이고, 마인크래프트의 RIFE는 아직 이 방식으로 재지 않았습니다.
- 60Hz 모니터에서는 게임이 52fps를 넘으면 넣을 자리가 없어 프레임 생성이 쉽니다.

144Hz 모니터 (2560×1440, 같은 노트북 GTX 1060, 게임 60fps라 배수 2.4, NVIDIA 전원 관리 "최대 성능 선호", 20초씩):

요약하면 144Hz에서도 출력, 시간 고르기, 멈춤, 추가 지연은 대부분 **좋음**이지만, 화면 전체에 프레임을 만들면 끊김이 아직 **나쁨**입니다 (DJMAX 분당 10~49번). 움직이는 곳만 프레임 생성 영역으로 지정하면 DJMAX에서 끊김과 건너뜀이 없었습니다 (12초 한 번). RIFE는 이 그래픽카드에서 60fps 게임을 따라가지 못합니다. 144Hz에서는 **블록 매칭 보간 + 영역 + 배수 자동**을 권합니다.

| 경우 | 출력 | 끊김 | 시간 고르기 | 멈춤 | 건너뜀 | 추가 지연 | RIFE 제때 |
|---|---|---|---|---|---|---|---|
| 마인크래프트, 블록 매칭 보간 | 100% 좋음 | 분당 14~20번 나쁨 | 0.09~0.11칸 좋음 | 0% 좋음 | 분당 14번 나쁨 | 0.4~0.6ms 좋음 | - |
| 마인크래프트, 블록 매칭 외삽 | 100% 좋음 | 분당 17~29번 나쁨 | 0.13~0.47칸 보통 | 0.2~0.4% 좋음 | 분당 35~61번 나쁨 | 0ms (늦추지 않음) | - |
| 마인크래프트, 블록 매칭 + 영역 | 100% 좋음 | 분당 20번 나쁨 | 0.10칸 좋음 | 0% 좋음 | 분당 9번 나쁨 | 0ms 좋음 | - |
| 마인크래프트, RIFE + 영역 | 99% 좋음 | 분당 70번 나쁨 | 0.48칸 보통 | 2.8% 보통 | 분당 253번 나쁨 | 11.4ms 보통 | 73% 나쁨 |
| DJMAX 1280×720, 블록 매칭 보간 | 99~100% 좋음 | 분당 10~49번 나쁨 | 0.06~0.32칸 좋음~보통 | 0~1.1% 좋음~보통 | 분당 0~15번 좋음~나쁨 | 0~0.3ms 좋음 | - |
| DJMAX 1280×720, 블록 매칭 + 건반 영역 | 100% 좋음 | 분당 0번 좋음 | 0.04칸 좋음 | 0% 좋음 | 분당 0번 좋음 | 0.1ms 좋음 | - |

- **고주사율 모니터를 주 모니터로 두어야 합니다.** Windows 10은 화면 합성을 주 모니터의 주사율로 해서, 주 모니터가 60Hz면 144Hz 모니터에서도 확대 화면이 초당 60장에 묶입니다 (게임 60fps와 같아져 프레임 생성이 쉽니다).
- **NVIDIA 그래픽카드는 OpenScaler의 전원 관리 모드를 "최대 성능 선호"로 두는 것을 권합니다** (NVIDIA 제어판 → 3D 설정 관리 → 프로그램 설정). 기본값에서는 GPU 사용률이 50~60%라 드라이버가 클럭을 낮춰, 마인크래프트를 띄운 채 확대만 해도(프레임 생성 끔) 출력이 초당 124~130장이었습니다. 바꾼 뒤에는 144장, 프레임 생성을 켜면 142~143장입니다.
- DJMAX처럼 게임 화면이 크면(1280×720) 게임이 GPU를 많이 쓰는 순간과 겹칠 때 몰려서 끊깁니다. **프레임 생성 영역을 움직이는 부분(건반)만 지정하면** 계산이 줄어 끊김이 더 줄어듭니다. **영역 추천**이 그 자리를 찾아 줍니다.
- **확대 중에는 OpenScaler의 GPU 스케줄링 우선순위를 "실시간"으로 올립니다** (1.3.10, RIFE를 쓸 때는 보통). 화면마다 할 일은 3ms 안팎이지만, 게임이 GPU를 많이 쓰는 순간과 겹치면 그 작업이 끝날 때까지 기다려 한 칸(6.9ms)을 넘겼습니다. 같은 곡에서 번갈아 재니 DJMAX 화면 전체 끊김이 분당 45~108번에서 10~49번으로, 외삽은 54번에서 15번으로 줄었고 게임 fps는 그대로(59.6~59.7)였습니다.
- 1.3.9에서는 합성과 움직임 찾기가 같은 결과를 덜 계산하도록 바꿔 DJMAX 화면마다 합성 GPU 시간이 0.9ms에서 0.4ms로 줄었습니다 (끊김 분당 109~152번에서 35~92번). 끊김 횟수는 곡의 어느 구간인지에 따라 크게 달라집니다. 마인크래프트 줄은 1.3.9에서 잰 값입니다.
- 60fps 게임은 프레임 간격이 16.7ms뿐이라 이 그래픽카드에서는 RIFE 결과를 제때 쓰기 어렵습니다 (영역을 지정해도 73%).
- 배수를 2배로 고정하면 144Hz를 60fps로 고르게 나눌 수 없어 같은 장면이 두 번 나오는 비율이 18~20%입니다. 고주사율에서는 배수를 **자동**(주사율까지 채우기)으로 두세요.

```mermaid
    A["게임 창 (낮은 해상도)"] --> B["화면 캡처, 게임 화면만 잘라내기"]
    B --> D["프레임 생성 (켠 경우): 움직임 찾기, 프레임 합성"]
    D --> E["업스케일 (FSR 1.0 등)"]
    E --> F["샤프닝"]
    F --> G["전체화면 출력, 커서 그리기"]
    G -. 클릭은 원래 창으로 .-> A
```

| 단계 | 쓰는 기술 | 하는 일 |
|---|---|---|
| 캡처 | Windows.Graphics.Capture | 대상 창의 화면을 GPU 텍스처로 받습니다. CPU로 복사하지 않아 빠릅니다 |
| 잘라내기 | Direct3D 11 | 창 테두리와 제목 표시줄을 빼고 게임 화면(클라이언트 영역)만 복사합니다 |
| 프레임 생성 | 컴퓨트 셰이더, RIFE(DirectML) | 원본 해상도에서 움직임을 찾고 새 프레임을 합성합니다. 확대 전에 하므로 계산량이 적습니다 |
| 업스케일 | 픽셀 셰이더 | 선택한 알고리즘으로 모니터 크기에 맞게 확대합니다 |
| 샤프닝 | 픽셀 셰이더 | 확대하면서 흐려진 윤곽선을 선명하게 만듭니다 |
| 출력 | 클릭이 통과하는 최상위 창 | 사용자는 확대된 화면을 보고, 입력은 게임으로 그대로 전달됩니다 |

### 7.1 마우스 좌표 변환

확대 화면은 클릭이 통과하는 창이라, 클릭은 항상 **실제 커서 위치** 아래의 창으로 들어갑니다.
그래서 실제 커서는 원래 창 안의 대응 위치에 두고, 사용자에게는 확대된 위치에 커서를 따로 그려 보여 줍니다.

1. 게임 창이 활성 상태에서 커서가 확대 화면 위로 들어오면, 실제 커서를 원래 창의 대응 위치로 옮깁니다.
2. 시스템 커서는 숨기고(Magnification API), 지금 커서 모양을 텍스처로 바꿔 확대된 위치에 그립니다.
3. 실제 커서가 원래 창 밖으로 나가면, 확대 화면의 같은 가장자리 바로 바깥으로 커서를 내보냅니다.
4. 다른 창으로 바꾸거나 확대를 끄면 커서를 화면상 보이던 위치로 되돌립니다.

### 7.2 프레임 생성

- **블록 매칭**: 원본을 여러 단계로 줄인 영상에서 큰 움직임부터 찾고, 단계를 올라가며 칸마다 움직임을 다듬습니다. 앞뒤 방향의 결과가 서로 맞는지 확인해 믿을 수 없는 칸은 덜 씁니다.
- **RIFE**: 게임 프레임 쌍마다 신경망을 따로 스레드에서 한 번 돌려 중간 시점의 움직임과 섞는 비율을 얻고, 합성은 원본 해상도에서 셰이더로 합니다. 신경망 입력을 줄여도 화면은 흐려지지 않습니다.
- **표시 시점**: 게임의 프레임 간격이 고르지 않아도 화면 속 시간이 일정하게 흐르도록, 최근 간격의 중앙값만큼 늦게 가는 표시 시계에 맞춰 생성할 시점을 정합니다.
- **게임별 학습**: 확대 중 가끔 게임 프레임 하나를 가리고 양옆으로 다시 만들어 정답과 비교합니다. 칸 크기, 탐색 범위 같은 값을 하나씩 바꿔 보며 점수가 오르면 채택하고, 기본값과도 주기적으로 비교해 나빠지지 않게 합니다.

### 7.3 FSR 1.0 구현

- 알고리즘 본체는 AMD 공식 헤더(`third_party/fsr`, MIT 라이선스)를 수정 없이 사용합니다.
- `src/fsr.hlsl`에서 입력 텍스처를 읽는 콜백과 픽셀 셰이더 진입점만 정의하고, 빌드할 때 `fxc`로 미리 컴파일합니다.
- 업스케일 단계는 EASU, 샤프닝 단계는 RCAS로 바뀌며, 샤프닝 강도(0~1)는 RCAS의 단계(stop) 값으로 변환합니다.

## 8. 알려진 한계

겪을 때 바로 할 수 있는 조치는 [3.7 문제 해결](#37-문제-해결)에 모았습니다.

- 전용 전체화면(Exclusive Fullscreen) 게임은 캡처할 수 없습니다. 게임을 창 모드로 실행해야 합니다.
- 화면을 한 번 더 그리는 구조라 약간의 입력 지연이 생깁니다. 프레임 생성의 보간은 여기에 게임 프레임 한 장 간격(30fps 게임이면 약 33ms)과 계산 시간이 더해지고, RIFE는 신경망 시간만큼 더 늦어집니다.
- 게임 fps가 모니터 주사율에 가까우면(주사율의 87% 이상) 프레임을 넣을 자리가 없어 게임 프레임만 보여 줍니다. 캡처도 모니터 주사율을 넘지 못합니다.
- Windows 10에서 주사율이 다른 모니터를 함께 쓰면 확대 화면은 주 모니터의 주사율로 나옵니다. 고주사율 모니터를 주 모니터로 두세요.
- 고주사율(144Hz)에서는 화면마다 계산할 시간이 6.9ms뿐이라, 그래픽카드가 게임과 함께 감당하지 못하면 가끔 화면이 한 칸 늦게 나옵니다. NVIDIA 그래픽카드는 전원 관리 모드를 "최대 성능 선호"로 두면 크게 줄어듭니다 ([6.2](#62-실시간-부드러운가-늦지-않은가)).
- 프레임 생성은 게임의 움직임 정보 없이 화면만 보므로 빠른 움직임, 화면 가장자리, 생김새가 같은 물체(리듬게임 노트 등), 제자리에서 밝기만 변하는 글자에서 깨질 수 있습니다.
- 게임 창이 모니터보다 커서 화면 밖으로 나간 부분은 Windows가 그리지 않으므로 잘라내고 보이는 부분만 확대합니다.
- 확대 중에는 실제 커서가 원래 창 크기 안에서 움직여 화면상 커서가 빨라집니다. 커서 속도 보정을 켜도 Windows 속도가 1~20 단계라 배율이 정확히 맞지 않을 수 있습니다. 바꾼 속도는 레지스트리에 저장하지 않고, 비정상 종료되면 다음 실행 때 되돌립니다.
- 게임 창과 확대 화면 사이에 다른 창이 겹쳐 있으면 클릭이 그 창으로 갈 수 있습니다.
- Windows 10에서는 캡처 중인 창에 노란 테두리가 표시될 수 있습니다 (Windows 11에서는 숨김).

## 9. 개발과 기여

### 9.1 직접 빌드하기

필요한 것: Visual Studio 2022 이상 ("C++를 사용한 데스크톱 개발" 워크로드), Windows 10 SDK, CMake

`x64 Native Tools Command Prompt for VS`를 열고:

```
git clone https://github.com/kojunpyo/OpenScaler.git
cd OpenScaler
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

빌드 결과는 `build/OpenScaler.exe`입니다. 프로젝트 폴더 경로가 아주 길면 MSVC 빌드가 실패할 수 있으니 짧은 경로(예: `C:\dev\OpenScaler`)에 두는 것을 권장합니다.

RIFE를 쓰려면 `rife` 폴더를 `OpenScaler.exe` 옆에 직접 만들어야 합니다. 자동 빌드(`.github/workflows/build.yml`)도 같은 방법으로 만듭니다.

| 파일 | 얻는 곳 |
|---|---|
| `onnxruntime.dll`, `onnxruntime_providers_shared.dll` | NuGet `Microsoft.ML.OnnxRuntime.DirectML` 1.24.4의 `runtimes/win-x64/native` |
| `DirectML.dll` | NuGet `Microsoft.AI.DirectML` 1.15.4의 `bin/x64-win` |
| `rife.onnx` | [RIFE v4.26 모델](https://huggingface.co/hzwer/RIFE)의 `flownet.pkl`을 `python -I tools/rife_export.py flownet.pkl rife.onnx`로 변환 (torch, onnx, onnxscript 필요) |

`main`에 푸시하거나 PR을 올리면 GitHub Actions가 자동으로 빌드하고, `v`로 시작하는 태그를 푸시하면 빌드 결과가 GitHub Releases에 올라갑니다.

<details>
<summary>명령줄 옵션 (테스트용)</summary>

```
OpenScaler.exe --target "창 제목 일부" --mode 4 --sharp 0.5 --fg --duration 10
```

| 옵션 | 설명 |
|---|---|
| `--target` | 제목에 이 문자열이 들어간 창을 바로 확대 |
| `--mode` | 0: Nearest, 1: Bilinear, 2: Bicubic, 3: Lanczos2, 4: FSR 1.0 |
| `--sharp` | 샤프닝 강도 (0 ~ 1) |
| `--integer` | 정수배 스케일링 사용 |
| `--compare` | 비교 모드로 시작 |
| `--cursor-speed` | 커서 속도 보정 켜기 |
| `--fg` | 프레임 생성 켜기 |
| `--fg-mult` | 배수 (2~4, 없으면 주사율까지 자동) |
| `--fg-quality` | 정밀도 (0: 낮음, 1: 기본, 2: 높음) |
| `--fg-block` | 방식을 블록 매칭 보간으로 (기본값) |
| `--fg-rife` | 방식을 RIFE 보간으로 |
| `--fg-extrapolate` | 방식을 블록 매칭 외삽으로 |
| `--fg-visualize` | 찾아낸 움직임을 색으로 표시 |
| `--fg-log` | 화면마다 표시 시점을 파일에 기록 |
| `--no-gpu-priority` | 확대 중에도 GPU 스케줄링 우선순위를 올리지 않음 (비교 측정용) |
| `--slowmo-auto` | `--target`으로 확대를 시작하고 지정한 초 뒤에 슬로모션 테스트 녹화 |
| `--slowmo-target` | 슬로모션 테스트에서 흉내 낼 주사율 |
| `--slowmo-seconds` | 슬로모션 테스트의 녹화 길이 (1~3초) |
| `--slowmo-dump` | 슬로모션 테스트에서 만든 프레임을 지정한 폴더에 BMP로 저장 |
| `--fg-selftest` | 계산으로 만든 영상으로 프레임 생성 품질을 재서 지정한 폴더에 저장하고 종료 |
| `--rife-bench` | RIFE 신경망 시간을 입력 크기별로 재서 지정한 폴더에 저장하고 종료. 환경 변수 `OPENSCALER_RIFE_PROFILE`에 파일 이름 앞부분을 주면 ONNX Runtime 연산별 기록도 남김 |
| `--fg-gaptest` | `--slowmo-dump`로 저장한 게임 프레임을 2~8칸 건너뛰어 생성하고, 건너뛴 게임 프레임과 비교해 두 번째 폴더에 저장하고 종료. 세 번째로 프로필(.json)을 주면 그 학습된 설정도 비교 |
| `--no-gui` | 설정 창 없이 실행 (단축키로만 조작) |
| `--console` | 로그를 보여 주는 콘솔 창 열기 |
| `--duration` | 지정한 초가 지나면 자동 종료 |

### 9.4 학습 데이터 올리기

잘 학습된 데이터([5.4](#54-학습-데이터-공유))는 [`shared-profiles`](shared-profiles) 폴더에 PR로 올립니다. GitHub 계정이 있으면 누구나 올릴 수 있습니다.

1. 저장소를 Fork하고, 내보낸 파일을 `shared-profiles/게임 이름.json`에 넣습니다. 파일 이름은 파일 안의 `name`과 같아야 합니다 (`\ / : * ? " < > |`는 `_`로 바꿈).
2. `python -I tools/profile_info.py "shared-profiles/게임 이름.json"`의 요약을 PR 본문에 붙입니다.
3. 게임 버전과 실행한 곳, 게임 창 크기, 프레임 생성 방식과 영역을 지정했는지, 어떤 장면을 몇 분 했는지 적어 주세요.

PR을 열면 GitHub Actions가 파일 형식을 검사합니다. **이미 있는 파일을 바꾸는 기준**은 같은 방식(보간 또는 외삽)의 "최근 채점 200회 평균, 기준보다 +dB"가 기존 파일보다 **0.2dB 넘게 높을 때**입니다. `python -I tools/profile_info.py "기존.json" "새 파일.json"`의 비교 결과를 붙여 주세요.
