# 프레임 생성 계획

블록 매칭 생성기, 학습 1, 2단계, RIFE 생성기를 구현했습니다. 학습 3단계(신경망 미세 조정)는 아직 없습니다. 실제 게임에서는 아직 확인하지 못했습니다.

## 사용자 요구

- 이 PC의 성능은 신경 쓰지 않는다. 테스트는 다른 기기에서 한다.
- 텀프로젝트이므로 한계가 있더라도 비교적 새로운 방식을 시도한다.
- 연결한 게임을 기록하고, 게임별 특징에 맞춰 프레임 생성 방식을 다르게 하며, 쓸수록 좋아지게 한다.
- 예: 리듬게임은 노트가 나오는 영역을 집중해서 부드럽게 만든다.

## 결정 사항

- 구현 범위: 옵션 B. 블록 매칭과 학습 1, 2단계를 먼저 완성한 뒤 RIFE 기반 생성기를 추가한다. 게임별 미세 조정은 일정이 남으면 진행한다.
- 테스트 기기 GPU: 아직 모른다. GPU 제조사에 묶이지 않게 만들고, 부담은 품질 설정으로 조절한다.
- 기본값: 배수는 주사율까지 자동, 방식은 보간, 움직임 격자는 1/4 해상도. 사용자가 따로 정하지 않아 제안값을 그대로 썼고 모두 설정에서 바꿀 수 있다.

## 구현한 파이프라인

`src/framegen.cpp`, `src/framegen_shaders.h` (D3D11 컴퓨트 셰이더)

진짜 프레임이 올 때:

1. 앞 프레임과 비교해 내용이 같으면 버린다. 캡처는 게임이 그리지 않아도 프레임을 보내기 때문이다 (30fps 창에서 초당 60번 온 것을 확인했다).
2. 휘도 피라미드를 만든다 (원본, 1/2, 1/4, 1/8, 1/16).
3. 두 방향(A->B, B->A)으로 블록 매칭을 한다. 1/16에서 전체 탐색하고, 후보(굵은 단계, 이전 프레임, 화면 지도)와 주변 탐색으로 세밀하게 내려간다. 그 자리에서 두 프레임이 같은 칸은 탐색 없이 움직임 0으로 둔다.
4. 후보가 모두 맞지 않는 칸은 1/8 영상에서 넓게 찾는다 (작고 빠른 물체용).
5. 양방향 결과가 서로 반대인지 검사해 신뢰도를 구한다.

화면을 그릴 때마다:

1. 표시 시계로 A와 B 사이의 시점 t를 구한다. 캡처 시각의 흔들림을 바로 따라가지 않도록 천천히 맞춘다.
2. 블록을 시점 t의 위치로 옮겨 적고(투영), 빈칸은 움직임이 작은 주변 벡터로 채운다. 벡터를 그대로 쓰지 않고 옮겨 적어야 작은 물체가 배경의 움직임에 묻히지 않는다.
3. 픽셀마다 주변 칸의 벡터와 "움직임 없음"을 후보로 놓고 두 프레임이 잘 맞는 후보에 비중을 준다. 한쪽에만 보이는 곳은 그쪽 색을 쓰고, 맞는 후보가 없으면 블렌딩한다.
4. 결과를 기존 업스케일에 넘긴다. 커서는 보간하지 않으므로 최신 위치로 그려진다.

게임이 주사율만큼 프레임을 내면 넣을 자리가 없으므로 그대로 보여 주고 지연도 늘리지 않는다.

## 게임별 학습

`src/game_profile.cpp`. 실행 파일 이름으로 게임을 구분하고 `profiles/게임이름.json`에 저장한다. 게임 화면은 저장하지 않는다.

| 단계 | 상태 | 내용 |
|---|---|---|
| 1. 설정 자동 조정 | 완료 | 1초마다 F0, F1, F2 중 F1을 가리고 현재 값과 후보 값으로 만들어 실제 F1과 비교한다. 6번 평균으로 후보가 더 좋으면 바꾼다. 3번마다 한 번은 기본값을 시험해 더 나으면 되돌린다. 대상: 칸 크기, 탐색 범위, 벌점, 허용치, 화면 지도 사용 여부 |
| 1-2. 외삽 학습 | 완료 (2026-11-16) | 블록 매칭 외삽을 쓰는 동안에는 F0, F1로 F2의 시각까지 외삽해 실제 F2와 비교한다. 기준은 F1 그대로. 학습값과 기록은 보간용과 따로 둔다 (`FgLearner interp, extrap`, 프로필 파일의 `x_` 값) |
| 2. 화면 지도 | 완료 | 화면을 32x18칸으로 나눠 칸별 주된 움직임, 움직이는 비율, 고정 비율을 쌓는다. 움직임 후보로 쓰고, 일반/리듬게임/스크롤 유형을 판단한다 |
| 3. 신경망 미세 조정 | 미착수 | RIFE 생성기와 일정이 먼저 필요하다 |

외삽 학습 재현 (`--fg-gaptest`의 `fg_gaptest_extrap_learning.csv`): 녹화의 앞 절반에서 게임 프레임 k, k+2로 k+4를 예측하며 360회 학습하고, 뒤 절반에서 비교했다. 다른 화면이 섞인 경우는 보간 재현과 같이 계산 장면을 24회씩 섞었다 (dB).

| 녹화 | 멈춤 (생성 없음) | 기본값 외삽 | 학습 후 (7가지 경우) |
|---|---|---|---|
| DJMAX 녹화 1 | 18.37 | 21.72 | 21.74 ~ 24.81 |
| DJMAX 녹화 2 | 18.17 | 20.61 | 21.50 ~ 23.37 |
| DJMAX 녹화 3 | 19.37 | 22.29 | 22.70 ~ 25.74 |
| 마인크래프트 (낮, 시점 회전) | 18.33 | 20.62 | 20.65 ~ 21.06 |

- 28가지 모두 기본값보다 좋아졌다. DJMAX 21가지 평균 +2.06dB. 섞이지 않은 경우 DJMAX 녹화 1에서 오차 감소율이 53%(기본값)에서 77%(학습 후)가 됐다.
- 외삽은 칸 16, 벌점 0.0005를 고르는 경우가 많았다. 보간 학습이 고르는 값과 달라, 학습값을 따로 두는 것이 맞았다.
- 실시간에서도 외삽 채점이 돌아 프로필에 따로 쌓이는 것을 마인크래프트로 확인했다 (30초에 채점 27회). 실제 플레이에서의 효과는 확인하지 못했다.

화면 지도는 강제로 쓰면 점수가 떨어지는 장면이 있었다 (pan_ui). 그래서 채점에서 더 좋을 때만 켜지는 값으로 만들었다.

게임 유형(일반/리듬게임/스크롤)은 화면 통계로 계산만 하고 생성 방식을 바꾸지 않는다. 예전 설정의 "게임 유형"은 "일반"이면 화면 지도를 끄는 것뿐이고 "자동"과 "리듬게임"의 동작이 같아 사용자가 오해할 수 있었다. 그래서 설정을 "화면 지도: 자동 / 끔"으로 바꾸고, 설정 창에서 유형 표시를 뺐다. 예전 설정 파일의 리듬게임(2)은 자동으로 읽는다.

### DJMAX에서 학습 효과 확인 (2026-11-15)

`OpenScaler.exe --fg-gaptest 덤프폴더 출력폴더 프로필.json`으로, DJMAX 플레이 화면의 진짜 프레임에서 기본값과 학습된 설정을 비교했다. 각 설정에는 실시간과 같이 긴 간격 처리를 덧붙였다. 2칸은 학습 채점과 같은 조건이다. 녹화 두 개의 값 (dB):

| 프로필 | 학습된 값 | 2칸 기본 -> 학습 | 4칸 기본 -> 학습 | 6칸 기본 -> 학습 |
|---|---|---|---|---|
| 11/03 (루트 `profiles`, 사용자 실행) | 칸 4, 벌점 0.0040, 허용 0.14, 지도 안 씀. 채점 116회, 채택 4회 | 29.6 -> 26.4 / 29.6 -> 27.1 | 24.3 -> 24.5 / 25.2 -> 25.4 | 22.0 -> 22.1 / 23.2 -> 23.2 |
| 11/11 (`build\profiles`, 측정 실행) | 칸 16, 벌점 0.0015, 허용 0.14, 지도 사용. 채점 226회, 채택 9회 | 29.6 -> 29.2 / 29.6 -> 29.3 | 24.3 -> 26.3 / 25.2 -> 27.0 | 22.0 -> 23.0 / 23.2 -> 24.0 |

- 학습이 자기 채점 조건(2칸)에서 오히려 나빠졌다. 11/03 프로필은 2.5~3.2dB, 11/11 프로필은 0.3~0.4dB 내려갔다.
- 11/11 프로필은 긴 간격에서 좋아졌는데, 학습된 칸 16 때문이다 (긴 간격 처리는 칸을 8 이상으로만 키운다).
- 화면 지도만 켜면 11/11 프로필에서 2칸 +0.15~0.19dB로 작은 효과가 있었다. 11/03 프로필의 지도는 결과가 기본값과 소수점까지 같아 실제로 쓰이지 않은 것으로 보인다. 이유는 확인하지 못했다.
- 짐작되는 원인: 학습은 화면이 움직이기만 하면 곡 선택, 결과, 플레이 화면을 가리지 않고 채점하고, 후보를 6번 평균해 조금이라도 나으면 채택한다. 메뉴 화면에서 크게 좋아진 후보가 플레이 화면을 나쁘게 해도 채택될 수 있고, 채택한 값을 기본값과 다시 비교해 되돌리는 장치가 없다.

### 학습 재현과 규칙 수정

`--fg-gaptest`는 덤프의 앞 절반으로 실제 프로그램과 같은 순서로 360회 학습하고, 보지 않은 뒤 절반의 2칸에서 기본값과 비교한다 (`fg_gaptest_learning.csv`). 다른 화면이 섞인 경우는 게임 프레임과 계산으로 만든 장면을 24회씩 번갈아 채점해 흉내 낸다.

- 플레이 화면만으로 학습하면 세 녹화 모두 +0.2~0.6dB 좋아졌다. 학습 방식 자체보다 다른 화면이 섞이는 것이 문제다.
- 섞으면 재현됐다. pan_ui를 섞으면 벌점이 0.004로 올라 DJMAX에서 -1.46dB (11/03 프로필과 같은 값), fade를 섞으면 -0.45dB. 채택이 15~16회로 많아 화면이 바뀔 때마다 값이 오갔다.

세 가지 규칙을 녹화 세 개 x 섞은 장면 7가지(없음 포함) = 21경우에서 비교했다 (학습값 - 기본값):

| 규칙 | 평균 | 가장 나쁜 경우 | 기본값보다 나빠진 경우 | 계산 장면 학습 (자체 테스트) |
|---|---|---|---|---|
| 이전: 6번 평균 | +0.25dB | -1.46dB | 3번 | +1.2 ~ +13.1dB |
| 12번, 중앙값과 이긴 비율 2/3, 기본값 되돌림 | +0.12dB | -0.45dB | 7번 | +0.4 ~ +8.7dB (느려짐) |
| 적용: 6번 평균 + 기본값 되돌림 | +0.34dB | -0.60dB | 1번 | +1.3 ~ +13.2dB |

적용한 규칙: 후보 시험 3번마다 한 번은 기본값(지도 사용 여부는 그대로)을 후보로 시험한다. 기본값은 6번 중 중앙값이 0보다 크고 절반 이상 이기면 돌아간다. 칸이 작아지는 계산 부담 기준은 기본값으로 돌아갈 때는 적용하지 않는다. 다른 후보는 이전과 같이 평균으로 판단한다. 이미 저장된 프로필도 다음 실행부터 기본값과 다시 비교된다.

- 화면을 구분해 따로 학습하지는 않았다. 메뉴에서 오래 머문 뒤에는 여전히 메뉴에 맞는 값이 될 수 있고, 게임 화면으로 돌아오면 기본값 되돌림으로 회복하는 구조다.
- 실제 게임에서 다시 학습시켜 확인하지는 못했다. 위 수치는 녹화 프레임으로 재현한 것이다.

### RIFE와 블록 매칭 비교

이웃한 두 프레임의 한가운데(t=0.5)와 1/4 지점(t=0.25). 입력 높이는 품질별로 빠름 256, 기본 384, 고품질 576이다.

1280x720, RIFE 기본 품질:

| 장면 | 블록 t=0.5 | RIFE t=0.5 | 블록 t=0.25 | RIFE t=0.25 |
|---|---|---|---|---|
| pan | 50.76 | 54.09 | 52.06 | 54.18 |
| pan_ui | 48.40 | 46.06 | 49.70 | 47.38 |
| sprites | 50.91 | 53.38 | 50.36 | 50.41 |
| rhythm | 22.64 | 28.06 | 24.16 | 28.01 |
| fast_pan | 38.98 | 52.96 | 40.89 | 53.15 |
| fade | 46.87 | 49.81 | 48.46 | 51.42 |

- RIFE는 작고 빠른 노트(+5.4dB)와 빠른 이동(+14dB)에서 크게 낫고, 밝기 변화에서도 블록 매칭의 약점이 없다.
- 고정 UI 장면은 RIFE가 낮다. 입력이 낮을수록 심해서 빠름 품질은 42.05dB, 고품질은 48.98dB이다. 합성에 "움직임 없음" 후보가 없고 움직임을 작은 해상도에서 가져오기 때문으로 본다.
- 신경망 시간(GTX 1060): 처음에는 자체 테스트에서 입력 높이 256은 24~28ms, 384는 40~50ms, 576은 69~74ms였다. 아래 "RIFE 속도" 절의 개선 뒤에는 각각 약 11ms, 22ms, 46ms다.

|---|---|---|---|---|---|
| 블록 매칭 | 59.8 | 1번 | 중앙값 16.7ms, 표준편차 6.9ms | 26 / 0 / 25번 (336칸 중) | 52ms |
| RIFE | 59.8 | 1번 | 중앙값 16.5ms, 표준편차 9.5ms | 13 / 3 / 15번 (335칸 중) | 76ms |

RIFE 실행에서 합성의 82%가 RIFE였고 나머지는 결과가 늦어 블록 매칭으로 대신했다. 같은 설정의 다른 실행에서는 85~100%였다.

## 측정으로 확인한 한계

- rhythm 장면은 블렌딩보다 낫지만 22dB대로 낮다. 생김새가 같은 노트가 여럿이면 다른 노트와 짝지어 일부가 깨진다.
- fade 장면은 블렌딩보다 낮다. 밝기 변화를 움직임으로 착각하는 경우가 남아 있다. 학습으로 많이 줄지만 없어지지는 않는다. 평균 밝기 차이를 빼는 방법을 시도했으나 매끄러운 무늬에서 오히려 크게 나빠져 되돌렸다.
- 점수는 계산으로 만든 영상의 값이다. 게임에서의 품질과 체감은 아직 확인하지 못했다.
- 학습은 채점 때마다 움직임 추정을 2번 더 하므로 1초에 한 번 GPU 부담이 늘어난다.
- 학습은 블록 매칭의 값만 조정한다. RIFE를 쓰는 동안에도 채점은 돌지만 RIFE 자체는 좋아지지 않는다.
- RIFE는 지연이 신경망 시간만큼 더 늘어난다 (위 표에서 52ms -> 76ms). 프레임 간격의 70%를 넘으면 입력 해상도를 자동으로 낮추고, 낮춘 값은 그 실행 동안 유지한다.
- RIFE는 시점 0.5의 움직임 하나를 비례해서 다른 시점에 쓴다. 근사라서 t=0.25에서 sprites 점수가 내려간다 (53.38 -> 50.41).
- 입력 크기가 바뀔 때마다 신경망 세션을 다시 만들어 몇 초 동안 블록 매칭을 쓴다.

## 사용자에게 이미 설명한 한계

- 보간은 입력 지연을 늘린다. 30fps 게임이면 약 33ms + 계산 시간(추정치)이고, 학습으로 줄어들지 않는다.
- 게임 프레임이 모니터 주사율 이상이면 넣을 자리가 없다. 60Hz 모니터에서는 60fps 미만일 때만 효과가 있다.
- 게임의 움직임 정보 없이 화면만 보므로 가장자리, UI 주변, 빠른 움직임에서 깨짐이 생긴다.
- 오차 점수와 체감은 다르다. F0과 F2는 실제 보간보다 간격이 2배 넓어 근사치다.
- 1, 2단계의 향상에는 끝이 있다. 계속 좋아지는 효과는 3단계가 필요하다.
- 3단계는 게임 화면을 디스크에 저장한다. 용량 제한과 삭제 기능을 넣고 외부로 전송하지 않는다.
- 개발 계획의 마지막이 12월이라 일정이 빠듯하다.

## 프레임 간격이 고르지 않을 때

표시 시계는 최근 간격의 중앙값만큼 늦게 가는데, 짧은 간격의 쌍이 도착하면 시계가 아직 그 앞 쌍에 있다. 최신 쌍만 쓰던 때는 시점이 0에 묶여 멈췄다가 건너뛰었다 (DJMAX 게임 오버 화면에서 발견). 이제 한 쌍 앞의 움직임과 RIFE 결과도 보관해 시계가 있는 쌍을 보여 준다.

간격을 1, 2, 2칸으로 되풀이하는 시험 창 (GTX 1060, 60Hz, 측정 구간 약 330칸):

| 경우 | 화면 진행 표준편차 | 멈춤 | 33ms 넘게 건너뜀 |
|---|---|---|---|
| 블록 매칭, 고치기 전 | 10.9ms | 41 | 41 |
| 블록 매칭, 고친 뒤 | 4.9ms | 0 | 13 |
| RIFE, 고치기 전 | 10.8ms | 74 | 69 |
| RIFE, 고친 뒤 | 3.7ms | 0 | 0 |

RIFE는 고친 뒤에도 이 GPU에서 신경망이 20ms 걸려 짧은 간격의 쌍을 제때 못 맞추므로 합성의 약 3분의 2를 블록 매칭이 대신했다 (이후 "RIFE 속도" 절에서 개선). 게임 화면에서는 아직 확인하지 못했다. DJMAX 결과 화면은 간격이 대부분 1칸이라 이 상황이 거의 생기지 않았다 (아래 DJMAX 절).

## 슬로모션 테스트

120Hz 모니터 없이 프레임 생성 결과를 보려고 사용자가 제안한 방식이다. 짧게 녹화해 목표 fps만큼 채운 뒤 화면을 그릴 때마다 한 장씩 보여 준다 (60 x N장을 N초 동안).

- 처음 제안은 캡처를 초당 60회보다 많이 하는 것이었지만, Windows.Graphics.Capture는 화면 합성 주기에 묶인다. 수직동기 없이 초당 4,608번 그리는 창도 60Hz 모니터에서는 60fps로 캡처됐다. 그래서 받을 수 있는 프레임을 모두 받고 나머지를 생성으로 채운다. 주사율이 높은 모니터에서는 같은 코드가 그만큼 더 받는다.
- 프레임 쌍마다 나눌 수는 첫 프레임부터의 시간과 목표 fps로 정한다. 30fps 게임은 쌍마다 4등분, 60fps 게임은 2등분이 되고 프레임이 빠진 구간은 더 많이 나눈다.
- 방식이 외삽이면 실시간과 같이 다음 진짜 프레임을 쓰지 않는다. 앞의 진짜 프레임 두 장으로 움직임을 구해 다음 진짜 프레임 전까지를 예측하고, 블록 매칭으로만 만든다. 녹화 첫 쌍은 앞 프레임이 없어 진짜 프레임을 반복한다.
- 측정 (GTX 1060, 60Hz, 800x450, 초당 600픽셀로 움직이는 막대, 1초 녹화, 목표 120fps):

| 생성기 | 표시 프레임 (진짜 + 생성) | 건너뜀 | 재생 시간 | 프레임당 이동 중앙값 (이론값 5.00) | 표준편차 |
|---|---|---|---|---|---|
| 블록 매칭 | 120 (58 + 62) | 0 | 1.98초 | 5.00픽셀 | 0.20 |
| RIFE | 120 (59 + 61) | 0 | 1.97초 | 4.99픽셀 | 0.40 |

- 위 측정 때는 녹화 직후 간격이 33~50ms로 벌어져 1초에 진짜 프레임이 58~59장만 들어왔고, RIFE의 큰 깨짐도 그 구간에서 나왔다. 프레임을 담을 텍스처를 녹화 전에 미리 써 두고 처음 0.25초를 버리도록 고친 뒤 막대 창에서 진짜 60장 + 생성 60장이 됐다.
- DJMAX RESPECT V 플레이 구간(1280x720)은 60fps로 캡처되어 60Hz에서는 실시간 보간이 들어갈 자리가 없다. 슬로모션으로 본 노트 이동은 블록 매칭과 RIFE 모두 표시 프레임당 9.0픽셀로 진짜 프레임과 같았다. 블록 매칭은 노트가 고정 글자 위를 지날 때 글자가 끌려가는 잔상이 있다.
- 확인할 수 있는 것: 생성 프레임의 품질, 깨지는 위치, 목표 fps에서의 움직임. 확인할 수 없는 것: 실제 지연, 실시간 끊김, 그 GPU에서 제때 만드는지. 실제 게임에서의 체감은 아직 확인하지 못했다.

사용법 (README에서 옮김, 2026-11-23):

- 시작: 확대 중 Alt+Shift+T는 바로, 설정 창의 버튼은 3초 뒤(게임 창을 누를 시간) 녹화를 시작한다.
- 순서: 정한 길이(기본 1초, `--slowmo-seconds` 1~3초)만큼 캡처한 프레임을 모두 녹화하고 내용이 같은 프레임은 버린다. 게임 프레임 사이를 목표 주사율(기본 120Hz, `--slowmo-target`)만큼 채운다. 시간 제한이 없어 느린 그래픽카드에서도 모든 프레임을 만든다. 화면을 그릴 때마다 한 장씩 보여 주므로 60Hz 모니터에서 120Hz를 흉내 내면 1초 분량이 2초 동안 재생된다.
- 재생 중 단축키: Alt+Shift+Space(멈춤), Alt+Shift+←/→(한 장씩), Alt+Shift+O(글자 끄기), Alt+Shift+T(끝내기). 이 단축키들은 재생 중에만 등록한다.
- 비교 모드를 켜면 왼쪽에 프레임 생성 없는 화면이 같은 속도로 나온다. 방식과 움직임 찾기는 프레임 생성 설정을 따르고, 외삽은 블록 매칭으로만 만든다.
- 재생 중에도 게임은 뒤에서 계속 돌아간다. 필요한 메모리가 4GB를 넘으면 시작하지 않는다.
- `--slowmo-dump 폴더`는 만든 프레임을 BMP(`frame_XXX_real.bmp`, `frame_XXX_gen.bmp`)와 게임 프레임 캡처 시각(`real_times.txt`)으로 저장한다. 화질 측정(`--fg-gaptest`)과 README 시연 화면에 쓴다.

## DJMAX RESPECT V에서 확인 (2026-11-11)

조건: GTX 1060, 60Hz, 1280x720 창을 1920x1080으로 FSR 확대, 곡 "너랑 있으면" (BPM 130, 게임 오버가 나지 않는 난이도). 게임에는 Enter만 입력했다 (그 밖의 입력은 게임이 비정상 동작으로 보고 꺼질 수 있다).

실시간 보간 (블록 매칭, `--fg-log`, 150초):

| 구간 | 캡처 | 프레임 생성 |
|---|---|---|
| 곡 진행 (약 130초) | 초당 59~60장 | 작동하지 않음. 진짜 프레임을 그대로 보여 주고 지연도 늘리지 않음 |
| 결과 화면 (약 15초) | 초당 39~47장 | 505칸 중 35칸에서만 작동 |

- 진짜 프레임 간격은 전체 기록에서 1칸 8,139번, 2칸 129번, 3칸 이상 31번이었다. 2칸 이상이 대략 초당 한 번 나온다.
- 결과 화면도 1칸 304번, 2칸 90번으로 간격의 중앙값이 주사율과 같아 대부분 넣을 자리가 없었다. 60Hz에서는 이 게임에서 실시간 효과를 볼 수 없고, 120Hz 이상 기기가 필요하다.

슬로모션 (곡 시작 약 36초, 1초 녹화, 목표 120fps). Enter를 누른 시점이 조금씩 달라 장면은 완전히 같지 않다.

| 방식 | 진짜 + 생성 | 노트 위치 | 노트가 BREAK 글자 위를 지날 때 | 노트 가장자리와 판정선 |
|---|---|---|---|---|
| 블록 매칭 보간 | 58 + 62 | 맞음 | 글자가 끌려가는 잔상 | 대체로 깨끗함. 67ms 공백에서는 블록 모양으로 깨짐 |
| RIFE 보간 | 60 + 60 | 맞음 | 깨끗함 | 깨끗함. 판정선 아래로 사라지는 노트에 작은 흔적 |
| 블록 매칭 외삽 | 60 + 59 (첫 장 반복 1) | 맞음 | 가끔 잔상 | 노트 위아래 가장자리가 번지고, 판정선에서 사라지는 노트가 깨짐 |

- 블록 매칭 녹화에는 진짜 프레임 사이가 약 67ms(4칸) 비는 곳이 한 번 있어 생성 7장으로 채웠다. 판정선 근처 노트와 BREAK 글자가 블록 모양으로 깨졌고, 위에서 내려오는 롱노트는 정상이었다. 120Hz 기기에서 실시간으로 돌리면 이 깨짐이 화면에 보인다.
- 외삽은 노트가 계속 내려간다고 예측하므로 판정선에서 갑자기 사라지는 노트를 맞히지 못한다. 원리상의 한계다.
- 슬로모션은 시간 제한이 없어 RIFE가 모든 프레임에 쓰였다. 실시간에서는 이 GPU에서 상당 부분을 블록 매칭이 대신하므로 이만큼 깨끗하다는 보장은 없다.
- 확인하지 못한 것: 게임 오버 화면에서 불규칙 간격 수정의 효과, 실시간 RIFE와 외삽, 다른 곡, 체감.

## 마인크래프트에서 확인 (2026-11-15)

조건: GTX 1060, 60Hz, 마인크래프트 Java판 26.3 (평화로움, 숲), 854x480 창을 1920x1080으로 FSR 확대. 게임에는 마우스 이동(시점 좌우 회전)과 W(앞으로 걷기)를 보냈다.

- 확대와 마우스: 정상. 마인크래프트는 마우스를 창 가운데에 묶어 두는데, 확대 중에도 시점 회전이 그대로 됐다.

| fade | 22.95 | 23.12 | +0.17 |

- 7가지 모두 기본값보다 좋아졌다. 벌점을 0.0005로 낮춘 경우가 4가지, 허용 밝기 차이를 0.14로 올린 경우가 5가지였다.

발견해 고친 문제: 학습 기록이 실행 파일 이름 `javaw.json`으로 저장돼, 다른 Java 게임이나 다른 버전과 기록을 나눠 쓰게 되어 있었다. javaw, java, python 같은 범용 실행 파일이면 창 제목에서 버전 번호와 뒤쪽 상태 표시를 뺀 이름을 붙이도록 고쳤다 (`Minecraft (javaw).json`, v1.0.2).

확인하지 못한 것: 실제로 걸어 다니며 하는 플레이, 다른 마인크래프트 버전과 다른 Java 게임, 체감.

### devicecheck.ps1로 다시 잼, 외삽의 멈춤 원인 (2026-11-16)

v1.1.1 릴리스 zip의 `tools\devicecheck.ps1`을 테스트 당일과 같은 방법으로 돌렸다 (마인크래프트 최대 프레임률 30, 시점을 계속 좌우로 회전, 방식마다 30초). 처음 20%를 뺀 약 20초 기준:

| 방식 | 출력 끊김 | 시간 고르기 | 멈춤 | 2칸 넘는 건너뜀 | 추가 지연 |
|---|---|---|---|---|---|
| 블록 매칭 보간 | 분당 2.9번 | 0.09칸 | 0% | 분당 0번 | 1.9ms |
| RIFE 보간 (입력 256, 10.8ms) | 분당 96번 | 0.44칸 | 1.1% | 분당 41번 | 14.8ms |
| 블록 매칭 외삽, 고치기 전 | 분당 2.9번 | 0.35~0.39칸 | 3.4~3.9% | 분당 121~141번 | 0ms |
| 블록 매칭 외삽, 고친 뒤 | 분당 2.9번 | 0.07칸 | 0% | 분당 0번 | 0ms |

외삽의 멈춤 원인: 게임은 평균 30fps지만 게임 프레임의 약 10%가 1칸(16ms) 만에 붙어 오고, 그 뒤 3칸(50ms)이 빈다. 외삽은 바로 앞 두 장의 움직임을 이어 가는데, 앞서 나갈 수 있는 거리를 "그 두 장 간격의 75%"로 묶어 두었다. 16ms 만에 붙어 온 쌍이면 12ms밖에 나가지 못해 t=1.75에서 화면이 멈추고, 다음 게임 프레임이 오면 한꺼번에 건너뛰었다. 상한을 "보통 프레임 간격(최근 간격의 중앙값)만큼"으로 바꿨다 (`ExtrapolateLimit`, 쌍 간격의 4배를 넘지 않게). 고치기 전 exe(v1.1.1)와 바로 이어서 같은 조건(1칸 간격 10~11%)으로 비교했다. 슬로모션의 외삽도 같은 상한을 쓴다.

- 상한을 늘린 만큼, 게임이 실제로 멈칫할 때는 물체가 조금 더 앞서 나갔다가 다음 프레임에서 되돌아갈 수 있다. 기록상 "되돌아감"은 0번이었지만 화면으로는 확인하지 못했다.
- 화질 측정 녹화도 게임을 30fps로 제한한 채 찍혀, 이웃한 프레임이 이미 33ms 간격이었다. 그래서 `--fg-gaptest`의 "2칸"이 15fps 게임 조건이 되어 점수가 낮았다 (오차 감소: 단순 섞기 34%, 블록 매칭 54%, RIFE 64%). 슬로모션 덤프에 게임 프레임의 캡처 시각(`real_times.txt`)을 함께 저장하고, `--fg-gaptest`가 그 간격을 읽어 `frame_ms` 열로 남기며, `fgquality.py`가 "앞뒤 프레임 사이 몇 ms (게임 몇 fps 조건)"으로 보여 주게 고쳤다. `devicecheck.ps1`은 화질 측정 녹화 전에 게임의 fps 제한을 풀도록 묻는다.

## 긴 간격 (게임이 멈칫한 쌍)

DJMAX에서 진짜 프레임 사이가 2칸 이상 벌어지는 일이 대략 초당 한 번 있었고, 67ms 공백에서 블록 매칭이 깨졌다.

측정 방법: `OpenScaler.exe --fg-gaptest 덤프폴더 출력폴더`. 슬로모션 덤프의 60fps 진짜 프레임에서 k와 k+간격으로 가운데를 만들고, 건너뛴 진짜 프레임을 정답으로 비교한다. 실제 게임 화면으로 긴 간격의 품질을 숫자로 잴 수 있다.

원인 조사:

- 탐색 범위는 원인이 아니다. 4칸 동안 노트가 약 36픽셀 움직이는데, 가장 굵은 단계의 탐색은 192픽셀까지 본다.
- 앞 쌍의 움직임 힌트도 원인이 아니다. 힌트를 쓰든 안 쓰든 차이가 0.2dB 안이었다.
- 깨지는 곳은 내용이 바뀌는 곳이다. 제자리에서 밝기와 대비가 바뀌는 BREAK 글자, 판정선에서 사라지는 노트, 위에서 새로 들어오는 노트. 간격이 길수록 이 변화가 커져 작은 칸이 다른 물체와 맞는다.
- "움직임 없음" 후보를 밝기 변화에 덜 민감하게 비교해 보았다. 무늬 없는 곳까지 적용하면 롱노트 위아래에 반투명한 띠가 생겼고, 무늬 있는 곳에만 적용하면 효과가 없어(+0.02dB) 되돌렸다.
- 2칸에서 4칸이 되면 블록 매칭이 약 7dB 떨어지는데, 칸 크기를 키우고 벡터 차이 벌점을 낮추면 대부분 회복된다.

적용한 처리: 쌍의 간격이 최근 간격 중앙값의 2.5배를 넘으면 칸 크기를 8픽셀 이상, 벌점을 0.0004 이하로 쓴다. 이때는 앞 쌍의 움직임을 힌트로 쓰지 않고 화면 지도 표본도 뽑지 않는다. 실시간과 슬로모션(보간, 외삽) 모두 같다. 함께 고친 것: 실시간 추정과 화면 지도 표본이 쌍의 실제 간격 대신 중앙값을 써서, 긴 간격에서 화면 지도의 움직임 힌트가 1칸 분량으로 계산되던 문제.

DJMAX 녹화 두 개 (RIFE 녹화 / 블록 매칭 녹화의 진짜 프레임, 1280x720, dB):

| 간격 | 시점 | 멈춤 | 블렌딩 | 블록 (이전) | 블록 (긴 간격 처리) | RIFE |
|---|---|---|---|---|---|---|
| 2칸 | 0.5 | 20.6 / 21.4 | 22.7 / 23.7 | 29.6 / 29.6 | 같음 (보통 간격) | 30.5 / 30.5 |
| 3칸 | 1/3 | 20.6 / 21.4 | 21.6 / 22.6 | 25.5 / 25.9 | 27.4 / 27.9 | 27.5 / 28.1 |

- 칸 16픽셀은 DJMAX 4칸에서 약 +3.5dB로 더 좋았지만, 움직이는 배경 위의 고정 UI(pan_ui)가 5dB 나빠져 8픽셀로 정했다. 8픽셀에서도 pan_ui는 2dB 내려간다.
- 벌점 0.0004가 빠른 이동에서 결정적이다 (fast_pan: 칸 8에 벌점 0.0008이면 15.8dB, 0.0004면 22.6dB).
- 보통 간격(2칸)에 같은 설정을 쓰면 오히려 내려가서 긴 간격에만 쓴다.
- 남은 문제: BREAK 글자처럼 제자리에서 밝기가 크게 바뀌는 글자는 여전히 찢어진다. 4칸 이상에서는 블록 매칭이 RIFE와 비슷해졌지만, 화면으로 보면 RIFE가 더 깨끗하다.
- 실시간 확인: 간격이 2, 4, 6칸으로 섞이는 시험 창에서 실시간 보간(블록 매칭, RIFE)과 슬로모션(보간, 외삽)이 정상 동작했다. 실시간 끊김 수치는 시험 창의 간격 분포가 실행마다 달라 비교하지 않았다. 실제 게임에서의 화면은 아직 확인하지 못했다.

## 다른 기기에서 확인할 것

고주사율 모니터 기기에서 2026-11-21, 22일에 확인할 예정이다. 등급 기준은 README의 "성능 평가 기준"이다.

준비:
- 릴리스 zip(v1.3.1 이상)을 푼다. `rife` 폴더와 `tools\devicecheck.ps1`이 들어 있다. 다른 OpenScaler는 꺼 둔다 (단축키가 겹친다).
- 게임을 창 모드로, 모니터보다 낮은 해상도로 켠다. 스크립트가 단계마다 게임의 최대 fps를 바꾸라고 묻는다.
- 이 PC에서 학습한 DJMAX 데이터를 **공유용으로 내보내기**로 파일을 만들어 가져간다 (공유 시험용).

기록 모으기 (약 10분, 파이썬 필요 없음):

```powershell
powershell -ExecutionPolicy Bypass -File tools\devicecheck.ps1 -Target "창 제목 일부" -Seconds 30
```

1. 기기 정보 (GPU, 주사율, 해상도)
2. `--rife-bench`: 입력 크기별 신경망 시간
3. 게임 fps를 주사율의 절반으로 맞추고 RIFE, 블록 매칭, 외삽을 30초씩 실시간 기록 (`--fg-log`, 프로필에 영역이 있어도 `--fg-region none`으로 화면 전체). 카운트다운이 끝나면 게임 화면이 계속 움직이도록 조작한다.
4. 블록 매칭 + 프레임 생성 영역(`-Region`, 기본은 가운데 세로 절반 `0.25,0,0.5,1`) 30초. 화면 전체 기록과 GPU 시간을 비교한다. 리듬게임이면 `-Region`을 건반 자리에 맞추면 더 정확하다.
5. 게임 fps를 주사율의 0.4배(144Hz면 57fps 정도)로 바꾸고 블록 매칭 30초. 게임 프레임 사이에 넣는 장수가 2장, 3장으로 번갈아 바뀌는 "정수배가 아닌 배수"에서 화면 속 시간이 고른지 본다.
6. 화질 측정용 슬로모션 덤프 2초. 녹화 전에 게임의 fps 제한을 풀라고 묻는다 (이웃한 프레임이 촘촘해야 30fps 조건까지 잴 수 있다). 덤프에는 게임 프레임의 캡처 시각(`real_times.txt`)도 남는다.
7. 영역 계산 시간 비교 (`--fg-regionbench`, 게임 조작 필요 없음): 덤프의 게임 프레임을 화면 전체와 영역으로 번갈아 400번씩 처리하며 GPU 시간을 잰다.
8. 그 기기의 `profiles` 폴더를 결과 폴더에 복사한다.

실시간 기록(1.3.1부터)에는 움직임 찾기와 합성의 GPU 시간, 작업 크기(영역을 지정하면 영역 크기)가 함께 남는다. `fgtiming.py`가 중앙값을 보여 준다.

가져와서 분석:

```powershell
python -I tools/test/fgtiming.py 결과폴더/fg_block.csv   # rife, ext, region, block_nonint도
OpenScaler.exe --fg-gaptest 결과폴더/dump 결과폴더/gap
python -I tools/test/fgquality.py 결과폴더/gap/fg_gaptest.csv
python -I tools/profile_info.py 결과폴더/profiles/게임.json
```

- 영역: `regionbench/fg_regionbench_summary.csv`로 판단한다. 실시간 기록(`fg_block.csv`, `fg_region.csv`)의 GPU 시간은 같은 조건에서도 두 배씩 흔들려 비교에 쓰지 않는다 (2026-11-18 이 PC의 데모 창 480x270: 화면 전체 0.57ms와 1.18ms). 이 PC 기준값은 아래 "영역 계산 시간"에 있다.
- 정수배가 아닌 배수: `fg_block_nonint.csv`의 "화면 속 시간 고르기"와 "멈춤"이 `fg_block.csv`보다 크게 나쁘면 개선 후보 "정수배가 아닌 배수"를 먼저 한다.

공유 시험 (사용자):
- 가져간 DJMAX 파일을 그 기기에서 **공유 데이터 가져오기**로 넣고, 게임별 학습 구역에 이 PC의 채점 기록과 학습값이 보이는지 본다.
- 그 기기의 게임 창 크기가 이 PC와 다르면, 몇 판 한 뒤 "기준보다 +dB"가 이 PC 때와 비슷한지 본다 (칸 크기가 원본 픽셀 단위라 다시 맞춰지는지).
- 그 기기에서 채점이 200회 넘게 쌓이면 내보내서 가져온다. `shared-profiles`의 첫 공유 후보가 된다.

직접 볼 것 (사용자만 확인 가능):
- 상태 표시(Alt+Shift+O)에서 출력 fps가 게임 fps보다 높은지
- 화면이 부드러워졌는지, 입력이 늦게 느껴지는지, 판정 타이밍이 어긋나는지
- 비교 모드(Alt+Shift+C)로 왼쪽(생성 없음)과 오른쪽(블록 매칭 보간, RIFE 보간)을 나란히 본 느낌
- 프레임 생성 영역을 건반 자리에 지정했을 때 경계에서 어색한 곳이 없는지
- RIFE: 1.3.2까지는 60Hz에서 출력 끊김이 많았다 (마인크래프트 분당 74번). 1.3.3에서 고친 뒤 끊김이 남는지, 늘어난 지연(데모 창 +44ms)이 체감되는지 본다. 기록의 "CPU 시간" 최대가 10ms를 넘으면 아직 GPU를 기다리는 곳이 있는 것이다.
- README 시연 화면 다시 찍기 (2026-11-22 완료): 유튜브 게임 영상(30fps)을 제목 표시줄 없는 640x360 창(WPF + WebView2)에 띄워 2560x1440 비교 모드로 확대하고, 영상 시각에 맞춰 슬로모션(목표 60fps, 2초)을 녹화해 한 장씩 넘기며 120장을 찍었다. Edge `--app` 창은 제목 표시줄을 클라이언트 영역 안에 그려 함께 캡처되므로 쓰지 않았다. 카메라가 계속 움직이는 영상은 1440x810 GIF로 55MB(64색도 22MB)라 같은 크기의 WebP(품질 85, 6MB)로 넣었다 (`docs/demo.webp`). 이후 차이가 잘 보이도록 같은 녹화를 일반 확대(Bilinear, 진짜 프레임만)와 FSR + RIFE로 한 바퀴씩 찍어 나란히 붙였다 (720x405 두 장). 2026-11-23에 같은 120장을 장마다 16~17ms(2초에 120장, 60fps)로 묶어 실제 속도로 바꿨다. 찍은 장마다 덤프 프레임과 맞춰 순서를 확인하고, 실행 시간이 모자라 바탕화면이 찍히거나 단축키 뒤의 상태 표시가 찍히지 않았는지 확인한다.

## 영역 계산 시간 (2026-11-18, GTX 1060)

`--fg-regionbench`로 같은 게임 프레임을 화면 전체와 가운데 세로 절반 영역(`0.25,0,0.5,1`)으로 번갈아 400번씩 처리한 GPU 시간의 중앙값.

| 덤프 | 넓이 | 움직임 찾기 (게임 프레임마다) | 합성 (생성 프레임 1장) |
|---|---|---|---|
| DJMAX 1280x720 (1회) | 50% | 1.358 -> 0.894ms (66%) | 0.537 -> 0.318ms (59%) |
| DJMAX 1280x720 (2회) | 50% | 1.346 -> 0.903ms (67%) | 0.533 -> 0.317ms (59%) |
| 데모 창 480x270 | 50% | 0.616 -> 0.539ms (87%) | 0.089 -> 0.063ms (71%) |

- 두 번 잰 값의 차이가 1% 안쪽이라 실시간 기록보다 훨씬 안정적이다.
- 넓이만큼 줄지 않는 것은 화면 크기와 상관없는 고정 비용(단계별 GPU 호출, 작은 단계의 피라미드)과, 영역 밖을 그리려고 화면 전체를 복사하고 붙이는 비용 때문이다. 화면이 작을수록 고정 비용의 비중이 커서 덜 준다.

## 설정 창과 단축키

"프레임 생성" 구역: 프레임 생성 켜기(Alt+Shift+F), 방식(블록 매칭 보간 기본값 / RIFE 보간 / 블록 매칭 외삽 실험, 설정 파일의 FgGenerator와 FgMethod를 묶은 것), 배수, 정밀도(FgQuality), 블록 매칭과 외삽일 때만 화면 지도(FgPreset)와 움직임 시각화, 상태(게임 fps, 움직임 찾기와 합성 시간). 옵션이 많으면 무엇을 골라야 할지 알기 어려워, 2026-11-16에 생성기와 보간/외삽을 하나로 묶었다. 잠시 RIFE를 기본값으로 했다가(v1.1.0), 게임별 학습이 블록 매칭에만 적용되므로 같은 날 블록 매칭 보간을 기본값으로 되돌렸다.
"게임별 학습" 구역의 상태 줄은 기본값과 다른 설정의 개수만 보여 주고, 자세한 값은 (?)에 담는다.
"게임별 학습" 구역: 켜기/끄기, 게임 목록, 채점 횟수와 학습된 값, 점수 그래프, 기록 지우기.
비교 모드에서는 왼쪽이 보간 없는 일반 확대, 오른쪽이 보간 결과다.

## RIFE 속도

`OpenScaler.exe --rife-bench 폴더`로 입력 크기별 신경망 시간만 잰다 (16:9, 30번 중 처음 3번 제외, GTX 1060). 환경 변수 `OPENSCALER_RIFE_PROFILE`에 파일 이름 앞부분을 주면 ONNX Runtime의 연산별 기록(JSON)도 남는다.

| 입력 | 처음 | 크기 고정 | + 출력 복사 제거 |
|---|---|---|---|
| 256x128 | 14.7ms | 5.4ms | 4.9ms |
| 320x192 | 16.8ms | 8.6ms | 6.7ms |
| 448x256 (빠름) | 19.4ms | 12.8ms | 9.9ms |
| 704x384 (기본) | 32.0ms | 27.2ms | 21.8ms |
| 1024x576 (고품질) | 70.0ms | 55.7ms | 43.3ms |

- 크기 고정: 모델은 크기가 바뀌어도 되게 내보냈기 때문에 실행할 때마다 크기 계산 연산 39개가 CPU에서 돌고, DirectML이 연산 280개를 하나씩 실행했다. 가장 작은 입력도 14.7ms가 걸린 이유다. 세션은 원래 크기마다 새로 만들므로 `AddFreeDimensionOverrideByName`으로 크기를 정해 주니 크기 계산이 미리 끝나고 고정 비용이 사라졌다. 모델 파일은 바꾸지 않았다.
- 출력 복사 제거: 신경망 출력(평면 5장)을 미리 만든 버퍼에 바로 받고, 픽셀마다 다시 늘어놓지 않고 세로로 이은 텍스처 하나로 올린다. 버퍼는 돌려 받아 다시 쓴다. 신경망 실행 외의 시간이 2~7ms에서 0.1ms 아래로 줄었다.
- 자체 테스트의 RIFE 점수는 고치기 전과 같다 (1280x720 기본 품질 6개 장면이 소수 둘째 자리까지 같음).
- 크기를 바꿀 때: 너무 느려서 입력을 낮추면 새 세션을 만드는 몇 초 동안 RIFE가 멈춰 그동안 모두 블록 매칭으로 대신했다. 이제 새 세션을 뒤에서 만들고 그동안은 이전 크기로 계속 돌린다.
- GPU 선택: DirectML 장치를 0번 대신 성능 우선 GPU(`DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE`)로 고른다. 내장 GPU와 외장 GPU가 함께 있는 노트북을 위한 것이며, GPU가 하나인 이 PC에서는 차이를 확인할 수 없다.

실제 캡처 경로 (`tools/test/fgform.ps1` 시험 창 640x360 -> 1080p, 60Hz, 10초 중 앞 20% 제외, RIFE 기본 품질):

| 진짜 fps | 경우 | RIFE를 쓴 비율 | 신경망 | 마지막 입력 높이 | 지연 중앙값 |
|---|---|---|---|---|---|
| 21 | 고치기 전 | 85% | 22.8ms | (256으로 낮춤) | 74.4ms |
| 21 | 고친 뒤 | 100% | 23.8ms | 384 | 75.9ms |
| 32 | 고치기 전 | 64% (다른 실행 46%) | 21.5ms | (256으로 낮춤) | 56.6ms |
| 32 | 고친 뒤 | 98% (다른 실행 92%) | 9.8ms | 256 | 45.1ms |

- 21fps에서는 기본 입력 384를 낮추지 않고 그대로 쓴다. 32fps에서는 384(22ms)가 프레임 간격의 70%를 넘어 256으로 낮추지만, 256이 10ms라 지연도 11ms 줄었다.
- 60fps 게임(간격 16.7ms, 예산 11.7ms)이면 이 GPU에서는 256 또는 192까지 낮아진다. 이 PC는 60Hz라 60fps 게임은 애초에 보간할 자리가 없어 재지 못했다.
- 남은 방법: 모델을 다시 내보내 반정밀도(fp16)로 돌리기 (GTX 1060은 fp16이 느려 이 PC에서는 효과를 볼 수 없다), 가장 고운 단계(block4)를 빼서 계산 줄이기, 입력과 출력을 CPU를 거치지 않고 GPU에서 주고받기.

## RIFE 실시간 끊김 (2026-11-18, 1.3.3)

재현: 데모 창(`tools/test/demoform.ps1`, 480x270, 실제 약 21fps)을 1080p로 확대하고 RIFE 보간으로 20~30초씩 실시간 기록. 1.3.2는 출력 끊김이 분당 4~88번으로 실행마다 크게 달랐다.

원인 조사: `--fg-log`에 CPU가 프레임 생성에 머문 시간(넘기기, 만들기)을 함께 남겼다. 끊긴 화면마다 게임 프레임을 넘기는 데 9~15ms가 걸렸다. 게임 프레임마다 GPU 결과를 기다리는 곳이 두 군데 있었다.

- 중복 프레임 검사: 새 프레임이 앞 프레임과 같은지 GPU에서 비교하고 바로 읽었다. 같은 프레임만 온 화면(새 프레임 0장)에서도 12~14ms가 걸렸다.
- RIFE 입력: 신경망 입력으로 줄인 프레임을 바로 읽었다.

GPU가 한가하면 둘 다 1ms 안쪽이지만, 신경망이 GPU를 쓰는 동안에는 그 작업이 끝날 때까지 기다려 화면을 제때 내지 못했다. 블록 매칭만 쓸 때는 끊기지 않았던 이유다. GPU 우선순위(`IDXGIDevice::SetGPUThreadPriority(7)`)를 올려 보았지만 정지 시간이 그대로여서 쓰지 않았다.

고친 것 (실시간 경로만, `FrameGen::SetRealtime`. 테스트와 슬로모션은 그대로 기다린다):

- 두 결과 모두 2ms까지만 확인하고, 끝나지 않았으면 다음 화면을 그릴 때 다시 확인한다. GPU가 한가하면 이 안에 끝나므로 블록 매칭의 동작은 같다.
- 중복 검사를 기다리는 동안 새 프레임은 빈 슬롯에 둔다. 그동안 다음 캡처가 오면 그때는 기다린다 (이미 한 화면 이상 지나 대개 끝나 있다).
- RIFE를 기다리는 시간: 신경망 시간 대신 게임 프레임 캡처부터 결과를 받을 때까지 잰 시간(최근 30개 중 두 번째로 큰 값, 프레임 간격의 90%까지)을 쓴다. 입력을 읽어 오는 시간과 화면 단위로 결과를 받는 시간이 들어 있다. RIFE를 쓸지는 그 중앙값이 프레임 간격보다 짧은지로 정한다. 처음에는 두 번째로 큰 값으로 정했더니 가끔 튀는 값에 RIFE가 꺼졌다 켜지며 표시 시계가 건너뛰었다 (RIFE를 쓴 비율 36~74%).

결과 (고치기 전 4번, 고친 뒤 3번, 20초씩, 중앙값):

|---|---|---|---|---|---|---|
| RIFE, 1.3.2 | 분당 13.5번 (4.2~63.6) | 분당 43번 | 0.28칸 | 1.3% | 21.5ms | 100% |

- 1.3.2의 RIFE 지연 21.5ms는 실제보다 작게 보인 값이다. 결과가 늦으면 앞 쌍을 붙잡고 있다가 건너뛰었다 (건너뜀 분당 43번, 멈춤 1.3%). 고친 뒤에는 결과를 기다리는 만큼 늦게 보여 주므로 지연이 늘고 화면은 고르다.

- 블록 매칭 지연 +1.7ms는 결과를 확인하는 짧은 대기다.
- 자체 테스트(`--fg-selftest`)의 화질 점수는 고치기 전과 모두 같고, 영역 시험도 통과했다. 외삽과 영역+RIFE 실시간 기록도 끊김 0번이었다.
- 남은 방법 (지연 줄이기): 입력을 신경망 스레드에서 직접 읽기(장치를 여러 스레드에서 쓰도록 설정해야 함), 지연을 보고 입력 해상도 낮추기. 실제 게임(마인크래프트)에서는 아직 다시 재지 않았다.

- 2배 고정은 144Hz에 60fps라 고르게 나눌 수 없어 멈춤이 18~20%다. 자동(주사율까지 채우기)을 써야 한다.
- 끊김의 원인: CPU 시간(넘기기+만들기)은 최대 6ms 아래였고, 프로세스 우선순위를 높여도 같았다 (분당 1003~1606번 대 1123~1190번). GPU 사용률은 50~66%였다. 끊김의 82%가 새 게임 프레임이 들어온 화면에서 났다 (전체 화면 중 새 프레임 비율 44%). 게임이 프레임을 그리는 순간과 OpenScaler의 움직임 찾기와 1440p 출력이 겹쳐 6.9ms 안에 끝나지 못하는 것으로 본다. 영역으로 작업을 줄이면 마인크래프트에서 끊김이 크게 줄었다 (DJMAX 영역은 줄지 않았다. 원인은 아직 모른다).
- 같은 조건을 다시 재면 크게 흔들렸다. 같은 마인크래프트 블록 매칭이 처음 실행에서 분당 128번, 30분 뒤 장면(땅을 내려다봄)에서 분당 1028~1190번이었다. Bilinear 확대는 FSR보다 조금 적었다 (분당 647~909번 대 1028~1153번).
- RIFE: 60fps 게임은 프레임 간격이 16.7ms라 신경망 입력이 128까지 낮아져도 결과를 제때 쓰는 비율이 23~41%(영역이면 86%)다. 이 GPU에서는 60fps 게임의 RIFE 실시간은 쓰기 어렵다. 마인크래프트 RIFE에서 입력 크기를 바꾸며 새 세션을 만들 때 CPU가 531ms, 154ms 멈췄다 (세션을 만드는 동안 GPU를 기다림).

화질 (`--fg-gaptest`, 오차 감소, 2칸 가운데 시점 / 4칸 가운데 시점):

| 게임 | 단순 섞기 | 블록 매칭 | 블록 (긴 간격 처리) | RIFE |
|---|---|---|---|---|
| 마인크래프트 | 36% / 34% | 59% / 46% | 59% / 59% | 87% / 75% |
| DJMAX | 43% / 35% | 89% / 55% | 89% / 73% | 90% / 81% |

### 144Hz 끊김 조사와 개선 (2026-11-22, 1.3.4)

`--fg-log`에 화면마다 GPU 작업 전체(프레임 생성부터 상태 표시까지)가 GPU에서 시작해 끝날 때까지의 시간을 함께 남겼다 (타임스탬프 쿼리, 열 20~23). `--no-fg`는 프레임 생성을 끈 기준을 잴 때 쓴다 (상태 줄의 출력 fps).

1. **GPU 클럭이 원인의 대부분이었다.** 마인크래프트를 띄운 채 확대만 해도(프레임 생성 끔) 출력이 초당 124~130장이었고, 가벼운 데모 창이면 144장이었다. GPU 사용률이 50~66%라 드라이버가 클럭을 1366~1442MHz(최대 1911MHz)에 두고, 제한 이유를 "여유(idle)"로 보고했다. NVIDIA 제어판에서 OpenScaler의 전원 관리 모드를 "최대 성능 선호"로 바꾸자(사용자가 변경) 확대만 하면 144장, 프레임 생성을 켜면 142~143장이 됐고, 제한 이유가 사라졌다. 프로세스 우선순위 높이기는 효과가 없었다.
2. **학습 채점이 1초에 한 번 몰렸다.** 최대 성능에서도 블록 매칭 끊김이 분당 79번 남았고, 끊긴 화면의 프레임 생성 GPU 시간이 5.7ms(보통 새 프레임 화면 2.75ms)였다. 채점은 움직임 찾기 2번, 합성 2번, 섞기를 한 화면에서 했다. 이제 채점을 네 단계(지금 값의 움직임 찾기 / 합성과 비교 / 후보 값의 움직임 찾기 / 합성과 비교, 기준)로 나눠 게임 프레임을 받아들이지 않은 화면에 하나씩 돌린다 (`RunEvaluationStep`). 그동안 채점할 프레임이 남아 있도록 보관 칸을 4개에서 8개로 늘렸고, 가장 오래된 프레임이 마지막 칸에 오면 남은 단계를 그 자리에서 끝낸다 (게임 fps가 주사율에 가까울 때). 채점은 전용 움직임 격자를 써서 실시간 움직임을 덮어쓰지 않는다. 테스트(실시간이 아닌 경로)는 예전처럼 한 번에 끝내며, 자체 테스트 결과는 학습을 포함해 모두 같았다. 실시간 채점은 1초에 한 번 꼴로 그대로 쌓였다 (마인크래프트 30초에 보간 26번, 외삽 26번, 데모 창 100fps와 30fps에서 25초에 21~23번).

결과 (144Hz, 최대 성능, 고치기 전(1.3.3)과 번갈아 잼, 20초씩):

| 경우 | 1.3.3 | 1.3.4 |
|---|---|---|
| 마인크래프트 블록 매칭 끊김 | 분당 148, 270번 | 분당 23, 28, 12, 21번 |
| 마인크래프트 외삽 끊김 | 분당 108번 | 분당 21, 29, 17번 |
| DJMAX 블록 매칭 끊김 | 분당 172, 136번 | 분당 76, 198번 (2단계로 나눈 중간 버전은 130, 332번) |
| DJMAX 외삽 끊김 | 분당 162, 65번 | 분당 80, 98번 |

- 마인크래프트는 5~10분의 1로 줄었다. DJMAX는 실행마다 흔들려 차이를 판단할 수 없다.
- 남은 끊김: DJMAX에서 71%가 새 게임 프레임이 온 화면이다. 1280x720이라 그 화면의 움직임 찾기 2.1ms와 합성 0.9ms가 더해져 프레임 생성만 3.7ms(90%는 4.7ms), 업스케일까지 4.9ms(90%는 6.0ms)로 한 칸(6.9ms)에 가깝다.
- DJMAX는 프레임 생성 영역(건반 `0.03,0,0.29,0.75`, 372x540)이 해결책이었다. 같은 곡에서 번갈아 재니 화면 전체 분당 50, 172번, 영역 분당 4.4, 9.3, 18.6번이었다 (건너뜀 0~4.6번, 출력 100%). 합성이 0.9ms에서 0.16ms로 준다.
- 시도했다가 되돌린 것: 새 게임 프레임의 움직임 찾기를 두 화면에 나누기 (정방향은 새 프레임 화면, 역방향과 맞춰 보기는 다음 화면, 표시는 한 칸 늦춤). 새 프레임 화면과 다른 화면의 GPU 시간이 4.0ms와 3.7ms로 고르게 됐지만, DJMAX 끊김은 분당 68~88번(나누지 않으면 47~70번)으로 줄지 않고 지연만 6.8ms 늘었다. 끊긴 화면은 전체의 1%였고 그 화면만 7.3ms로 튀어, 우리 작업이 몰려서라기보다 게임의 GPU 작업과 가끔 겹쳐 기다린 것으로 본다. 새 게임 프레임을 화면을 내보낸(Present) 뒤에 넘기기 (데모 창 출력 137.3 -> 139.6fps로 조금 나았지만 마인크래프트에서 차이가 없고 지연이 8ms 늘었다, 클럭이 낮던 때 잼), GPU 대기열 2장 (출력이 119fps로 더 나빠짐).

남은 개선 후보:
1. 영역 추천은 1.3.5에서 만들었다 (위 "영역 추천"). 남은 것: 리듬게임으로 판단되면 설정 창에서 먼저 권하기.
2. RIFE: 60fps 게임에서는 결과를 제때 쓰지 못한다 (영역 없이 23~31%). 입력 크기를 바꿀 때 CPU가 최대 531ms 멈춘다.
3. 설정 창에 "주 모니터 주사율"과 "최대 성능" 안내 (지금은 README에만 있음).

## 영역 추천 (2026-11-22, 1.3.5)

설정 창 "영역" 줄의 **영역 추천**: 최근 10초 동안 자주 바뀐 곳을 감싼 사각형으로 영역 편집 창을 띄운다. 사용자가 다듬어 Enter로 저장한다.

- 학습의 화면 지도는 쓰지 않는다. 메뉴와 결과 화면이 섞여 오래 쌓인 값이라 DJMAX 지도에서 건반이 구분되지 않았다.
- 게임 프레임마다 하던 중복 프레임 검사의 묶음별 차이(GPU에서 이미 읽어 오던 값)를 쓴다. 추가 GPU 작업은 없다. 검사 단계를 1/8에서 1/4로 바꿔 묶음이 원본 32픽셀이 됐다 (자체 테스트 결과는 같음).
- 묶음마다 "차이가 밝기 약 1.6/255를 넘은 시간의 비율"을 10초 지수 평균으로 쌓는다. 처음 3/255로 두었더니 어두운 마인크래프트에서 시점을 돌려도 칸마다 10~30%만 바뀐 것으로 나왔다.
- 추천: 상위 5% 칸 비율의 40% 이상인 칸을 이웃끼리 묶고, 합이 가장 큰 덩어리를 감싼 뒤 한 칸씩 넓힌다. 그런 칸이 화면의 60%를 넘거나 사각형이 85%를 넘으면 "좁힐 곳이 없다"고 알린다. 5초 넘게 모으지 못했거나 거의 안 움직였으면 그렇게 알린다. 이미 영역을 지정했으면 그 안에서 더 좁힌다.
- 결과: DJMAX "너랑 있으면" 플레이 중 15초, 25초 모은 두 번 모두 `0, 0, 0.325, 0.8`(건반, 판정선, 테두리). 점무늬 배경 영상은 빠졌다. 마인크래프트(시점 회전)는 "좁힐 곳이 없다". 데모 창은 가장 많이 움직이는 왼쪽 사각형과 빗금 부분 (왼쪽과 오른쪽이 같은 장면이라 한쪽만, 노트 칸은 노트가 드물어 빠짐).
- 시험: `--region-recommend 초` (확대 후 그 시간이 지나면 추천 결과와 묶음별 비율을 출력, 편집 창은 띄우지 않음). 설정 창 버튼은 데모 창으로 눌러 편집 창이 추천 영역으로 열리는 것과 Esc로 취소하면 저장되지 않는 것을 확인했다.
- 한계: 덩어리 하나만 고르므로 움직이는 곳이 떨어져 두 군데 있으면 하나만 잡는다. 배경 영상이 크게 움직이는 리듬게임이면 배경을 고를 수 있다.

## 확대 화면 위 메뉴 (2026-11-22, 1.3.6)

모니터가 하나면 확대 화면이 설정 창을 덮어 영역 추천 같은 기능을 쓸 수 없다. Alt+Shift+G로 확대 화면 오른쪽에 설정 패널을 그린다.

- 그리기: 확대 화면을 그린 뒤(상태 표시 다음) Present 전에 ImGui를 그린다. 설정 창과 컨텍스트를 따로 두고 글꼴 아틀라스는 함께 쓴다. 설정 구역(업스케일~화면 표시)은 `DrawSettingsBoxes` 하나를 두 곳이 같이 쓴다. 대상 창 고르기는 빼고 확대 상태와 중지 버튼을 둔다. 파일 창을 쓰는 공유 버튼은 확대 화면 뒤로 숨으므로 뺐다.
- 입력: 메뉴가 열리면 확대 화면 창에서 `WS_EX_TRANSPARENT`를 빼고 `WM_NCHITTEST`를 `HTCLIENT`로 돌려 마우스를 받는다. `WS_EX_NOACTIVATE`와 `WM_MOUSEACTIVATE`의 `MA_NOACTIVATE`로 게임 창의 포커스는 그대로 둔다 (마인크래프트가 일시정지되지 않음). 커서 변환은 영역 편집 때처럼 멈춘다. 확대 화면 창은 확대할 때마다 새로 생기므로 ImGui Win32 백엔드 대신 창 프로시저가 마우스 메시지를 넘긴다. 키보드는 받지 않는다 (지금 설정에는 글자 입력이 없다).
- 영역 지정/추천: 편집 창을 띄운 동안 메뉴를 숨기고, 끝나면 다시 보여 준다. 메뉴를 닫을 때 게임 창이 앞 창이 아니면 되돌린다.
- 확인: 데모 창에서 설정 창 없이(`--no-gui --overlay-menu`)와 설정 창과 함께(두 컨텍스트) 그려짐, Alt+Shift+G로 열고 닫음, 정수배 체크 켜고 끔(설정 파일이 원래대로 돌아옴), 닫은 뒤 클릭이 아래 창으로 통과함, 영역 지정 중 메뉴가 숨었다가 Esc 뒤 다시 나옴. 마인크래프트는 일시정지 메뉴에서 체크가 눌리고 게임이 앞 창으로 남았지만, 게임 중에는 게임이 커서를 가운데 붙잡아 메뉴를 누를 수 없었다 (메뉴와 README에 안내).
- 비용: 메뉴를 연 동안 화면마다 GPU 시간이 중앙값 3.25 -> 3.98ms (데모 창 1440p, 144Hz).
- 시험 옵션: `--overlay-menu` (확대가 시작되면 메뉴를 연다. DJMAX에는 단축키를 보낼 수 없어 이것으로 시험한다).

### 확대 시작 팝업 (1.3.7)

확대를 시작하면 메뉴를 열고 가운데에 "프레임 생성 영역을 지정할까요?" 팝업(예 / 아니오, 사용자가 정한 문구)을 띄운다. 예를 누르면 메뉴를 숨기고 확대 화면 창이 다시 클릭을 통과시켜 게임을 계속할 수 있게 한 뒤, 위쪽에 "추천 영역 계산 중..."과 진행 막대를 보여 준다. 누른 뒤의 10초만 모아(`ResetChange`, `RecommendRegion(.., 10)`) 추천 영역이 나오면 영역 편집 창을 그 영역으로 띄운다. 화면 대부분이 움직이면 "직접 지정하기 / 닫기"를 묻는다. 프레임 생성이 꺼져 있었으면 예를 누를 때 켠다. 계산 중에는 Alt+Shift+G로 취소한다. 설정 창을 쓸 때만 띄우고, `--no-gui`(측정, 시험)에서는 `--region-wizard`를 줄 때만 띄운다.

- 확인 (데모 창): 팝업이 뒤를 어둡게 하고 가운데에 뜸, 예를 누르면 계산 중 안내(4/10초)가 뜨고 10초 뒤 편집 창이 추천 영역으로 열림 (세 번 모두 10초). 한 번은 데모 창 자체가 그리기를 멈춰(캡처 0fps) 안내가 0/10초에서 기다렸다. 게임 화면이 멈추면 계속 기다리므로 Alt+Shift+G로 취소한다.
- DJMAX ("너랑 있으면" 플레이 중): 예를 누르고 10초 뒤 편집 창이 건반과 판정선 영역 `0, 0, 0.325, 0.8`로 열렸다. 팝업 클릭은 확대 화면 창이 받아 게임에는 Enter 외의 입력이 가지 않았다.
- 마인크래프트: 계산 중 안내가 뜬 동안 시점 회전 입력이 게임으로 갔고, 10초 뒤 "좁힐 곳을 찾지 못했어요" 팝업(직접 지정하기 / 닫기)이 떴다. 게임 중에는 커서가 붙잡혀 있어 팝업을 누르려면 게임 메뉴(Esc)를 먼저 연다.

## 144Hz GPU 시간 줄이기 (2026-11-23, 1.3.9)

1.3.4 뒤에도 DJMAX(1280x720) 화면 전체 프레임 생성은 144Hz에서 분당 100번 넘게 끊겼다. 화면마다 GPU 시간을 줄이는 쪽을 찾았다. 측정은 같은 노트북, 144Hz 주 모니터, "최대 성능 선호", DJMAX "너랑 있으면" 플레이 중(Enter만 보냄)과 마인크래프트 시점 회전, 20초씩 번갈아.

시도한 것:

| 방법 | 결과 | 채택 |
|---|---|---|
| GPU 대기열 2장 (`SetMaximumFrameLatency(2)`, 버퍼 3장) | 출력 108fps, 끊김 분당 2,000번. 다시 확인해도 나빴다 | 아니요 |
| 정밀도 낮음 (칸 8 이상) | 움직임 찾기 시간이 거의 그대로 (1.52 -> 1.50ms). 비용은 가장 굵은 단계의 전체 탐색과 1/8 단계의 넓은 탐색에 있다 | 아니요 |
| 가장 굵은 단계를 한 칸 건너 찾기 | 움직임 찾기 15~25% 감소, 게임 녹화 품질은 같음(±0.2dB). 그러나 자체 테스트의 빠른 이동에서 -0.2~-1.4dB (가장 나은 두 곳 주변을 다시 찾아도 긴 간격에서 -1dB) | 아니요 |
| 넓은 탐색을 한 칸 건너 찾기 | 움직임 찾기 30% 감소, DJMAX 녹화에서 -0.3~-0.6dB (작은 노트를 놓침). 실시간 끊김도 더 줄지 않음 | 아니요 |
| 합성: 같은 벡터의 후보는 한 번만 계산 | 결과가 같고(PSNR 같음) 합성 0.9 -> 0.4ms (DJMAX 실시간), 1280x720 자체 테스트 0.73~1.08 -> 0.40~0.73ms | 예 |
| 블록 매칭: 굵은 단계 주변 9칸, 움직임 없음, 이전 프레임 후보 중 이미 본 벡터는 건너뛰기 | 결과가 같고 DJMAX 녹화의 움직임 찾기 1.25 -> 1.10ms | 예 |

- 합성은 픽셀마다 주변 네 칸의 벡터와 "움직임 없음"을 후보로 놓고 후보마다 12번 텍스처를 읽는다. 멈춘 곳이나 함께 움직이는 배경에서는 네 칸이 같은 벡터라, 앞에서 계산한 색과 오차를 그대로 쓴다. 게임 프레임마다가 아니라 화면마다 돌기 때문에 144Hz에서 효과가 크다.
- 자체 테스트(`--fg-selftest`)는 1.3.8과 같다 (학습 재현만 소수점 넷째 자리 차이, 부동소수점 순서). `--fg-gaptest`의 CSV에 블록 매칭 GPU 시간 열(`block_estimate_ms`, `block_synth_ms`)을 더했다.
- 남은 끊김은 시간이 1초 간격이 아니라 몇 번씩 몰려 나고, 그 화면만 프레임 생성 GPU 시간이 5ms 넘게 튄다 (나머지 업스케일 시간은 그대로). 게임이 GPU를 많이 쓰는 순간과 겹친 것으로 본다. 확대 화면 창은 클릭을 통과시키려고 레이어드 창이라 화면 합성(DWM)을 거친다.

- 같은 버전도 곡의 구간에 따라 끊김이 2배 넘게 달라진다 (곡 끝에서 게임 fps가 57로 떨어진 실행이 92번).

## GPU 스케줄링 우선순위 (2026-11-23, 1.3.10)

1.3.9 뒤에 남은 끊김은 몇 번씩 몰려 나고, 그 화면만 프레임 생성 GPU 시간이 5ms 넘게 튀었다. 우리 작업은 화면마다 3ms 안팎이므로, 게임이 GPU를 쓰는 동안 기다리는 시간으로 보고 프로세스의 GPU 스케줄링 우선순위를 올려 보았다. 이 PC는 하드웨어 가속 GPU 스케줄링이 켜져 있다 (`HwSchMode` 2). 관리자 권한 없이도 `D3DKMTSetProcessSchedulingPriorityClass`(gdi32)가 성공을 돌려주었다.

| 방법 | DJMAX 화면 전체 끊김 (분당) | 비고 |
|---|---|---|
| 보통 (1.3.9) | 64, 108, 45, 49, 63.8 | |
| 높음 (등급 4) | 45, 108 | 차이 없음 |
| 실시간 (등급 5) | 30, 20, 15, 49, 9.9 | 화면마다 GPU 시간 중앙값 3.4 -> 2.6ms, 게임 59.6~59.7fps 그대로 |
| 실시간 + 건반 영역 | 0 (보통이면 12.5) | 건너뜀도 0 |
| 외삽, 실시간 | 14.7 (보통이면 54.2) | |
| `IDXGIDevice::SetGPUThreadPriority(7)` | 1.3.3 RIFE 시험에서 효과 없음 | |

- 같은 곡에서 번갈아 쟀다 (20초씩, 마지막 줄의 9.9와 63.8은 `UpdateGpuPriority`를 넣은 최종 빌드에서 `--no-gpu-priority`와 비교).
- 마인크래프트는 밤 동굴 장면이라 블록 매칭이 둘 다 거의 끊기지 않아 비교가 되지 않았다 (GPU 시간 중앙값 2.9 -> 2.1ms). RIFE는 끊김이 564~736 -> 436~489번으로 줄었지만 게임이 58.3~58.6 -> 57.1~58.2fps로 조금 느려졌다.
- 그래서 RIFE를 쓸 때는 보통으로 둔다. 신경망은 GPU를 길게 쓰므로 실시간 우선순위면 느린 그래픽카드에서 게임과 바탕화면 합성을 밀어낼 수 있다. 블록 매칭과 외삽, 프레임 생성을 끈 확대는 실시간이다. 확대를 멈추면 보통으로 되돌린다.
- 남은 것: 다른 기기(특히 GPU가 거의 꽉 찬 게임)에서 게임 fps가 떨어지지 않는지, 60Hz에서도 차이가 있는지.

## Lossless Scaling과 비교 (2026-11-23, 1.3.10)

Lossless Scaling 3.2.2 (Steam)와 같은 PC에서 번갈아 쟀다. README 6.3에 요약했다.

측정 방법:
- 화면 캡처로 재는 방법은 쓸 수 없었다. Windows.Graphics.Capture로 모니터를 받아 장면 간격과 내용 해시를 남기는 시험 옵션을 만들었는데, Lossless Scaling이 자기 창을 캡처에서 빼서(장면의 99.9%가 같은 바탕화면) 재지 못했다. 이 옵션은 넣지 않았다.
- PresentMon 2.6.0 (Intel, MIT, 980KB, 서명 확인)으로 화면 표시 시각을 기록했다. ETW라 관리자 권한이 필요하다(사용자가 UAC 승인). `--date_time`의 시각이 이 PC에서 9시간 앞서 적혔다.
- PresentMon 콘솔 창이 앞 창이 되면 관리자 창이라 보통 권한의 스크립트가 다른 창으로 포커스를 옮기지 못한다 (게임이 멈춘 채로 13구간을 버렸다). `-WindowStyle Hidden`으로 띄운다.
- Lossless Scaling 조작: "업스케일" 버튼을 누르면 5초 뒤 앞 창을 확대하므로 그 사이에 게임 창으로 바꾼다. 끌 때도 버튼을 누른다. Ctrl+Alt+S는 Lossless Scaling 창을 앞에 두고 보내면 끄지 못했다 (두 프로그램이 함께 돈 구간 3개를 버렸다). DJMAX에는 Enter와 창 바꾸기만 했다.
- 설정은 `%LOCALAPPDATA%\Lossless Scaling\Settings.xml`을 백업하고 고친 뒤 Lossless Scaling을 다시 실행해 바꿨다. "성능 우선"은 `LSFGSize`(BALANCED/PERFORMANCE), 흐름 배율은 `LSFGFlowScale`, 모드는 `LSFG3Mode1`(ADAPTIVE/FIXED)과 `LSFG3Multiplier`다. 끝나고 백업으로 되돌렸다 (해시 확인).
- 분석: `tools/test/pmcompare.py` (구간 시작/끝 시각 파일로 나눔, 켠 뒤 2초는 뺌).

- 비교하지 못한 것: DJMAX에서의 설정별 차이, 실제 체감.

화질 비교 (2026-11-23):

처음에는 Lossless Scaling의 출력을 얻지 못했다.
- `Lossless.dll`이 `SetWindowDisplayAffinity`를 부른다. 캡처 API가 DXGI(기본)일 때 출력 창(클래스 `LosslessScaling`, 제목 없음, 2560x1440, 아래에 `LosslessScalingBlk`)이 캡처에서 빠져 Windows.Graphics.Capture와 GDI에는 아래 바탕화면이 찍혔다. Lossless Scaling의 안내: WGC 캡처면 어떤 프로그램으로도 녹화할 수 있고 DXGI면 OBS 게임 캡처가 필요하다. WGC는 Windows 11 24H2부터라 이 PC(Windows 10)에서는 쓸 수 없었다 (바꾸면 검은 화면).
- NVIDIA 앱 스크린샷과 녹화는 확대 중에 파일이 생기지 않았다. 3.2.2에는 자체 녹화 기능이 없다 (Ctrl+F11도 반응 없음).
- OBS를 보통 권한으로 띄워 게임 캡처를 창 클래스로 지정했을 때는 붙지 않았다.
- 해결: 사용자가 OBS와 Lossless Scaling을 모두 관리자 권한으로 실행하고 OBS 게임 캡처로 Lossless Scaling을 잡았다. 녹화 설정은 1920x1080, 60fps, 높은 품질이라 2560x1440 출력의 왼쪽 위만 담겼다.

방법:
- 원본: 고주사율 확인 때 60fps로 녹화한 실제 게임 프레임(DJMAX 120장, 마인크래프트 119장)을 창에 한 장씩 건너뛰어 30fps로 보여 준다. 처음에는 GDI+ DrawImage로 그렸는데 한 장에 21ms가 걸려, Lossless Scaling과 OBS, 게임이 함께 돌자 초당 10장 정도로 느려졌다(첫 녹화는 버림). 미리 만든 GDI 비트맵을 BitBlt로 옮기도록 바꿔 0.5ms가 됐고, 녹화하는 동안 1,800번 그리면서 빠진 장이 없었다.
- Lossless Scaling: LSFG 3.1 고정 2배, FSR. 관리자 권한이어도 전역 단축키(Ctrl+Alt+S)는 원본 창을 앞에 두고 보내면 받았다. 녹화의 각 장면을 반으로(마인크래프트는 1/3로) 줄여 원본 120장과 맞추고, 실제 프레임 k와 k+2 사이에 나온 장면을 정답 k+1과 비교했다. 녹화 동영상은 Media Foundation으로 풀었다 (임시 시험 코드, 넣지 않음).
- OpenScaler: 같은 원본 창에 슬로모션 테스트(목표 60fps, 3초, `--slowmo-dump`)를 돌려 생성 프레임을 그대로 저장하고 같은 방법으로 맞췄다.
- 비교 영역은 녹화에 담긴 원본 좌표(DJMAX x 0~960, y 30~540 / 마인크래프트 x 0~640, y 20~360)다. Lossless Scaling의 FPS 표시가 있는 위쪽 줄은 뺐다.

|---|---|---|---|---|---|---|
| DJMAX | 43.6dB | 20.4~20.6dB | 22.6~22.9dB, 40% | 28.6dB, 85% (153장) | 30.8dB, 90% (77장) | 30.0dB, 89% (88장) |

- 같은 순간을 나란히 붙인 사진: `docs/quality_ls_djmax.png`, `docs/quality_ls_minecraft.png`. DJMAX에서 블록 매칭은 글자와 노트에 칸 모양 깨짐, Lossless Scaling은 노트 가장자리가 조금 휨, RIFE가 가장 깨끗했다. 마인크래프트에서 블록 매칭은 질감이 흐려졌다.

- 시험 중 주의: 이미 열려 있던 사용자의 OBS를 닫아 버린 일이 있었다. OBS를 자동으로 다룰 때는 실행 중인 OBS가 있으면 시작하지 말고, 직접 띄운 프로세스만 닫는다.

## 화면 기준 끊김 (2026-11-23, 1.3.10)

PresentMon으로 화면에 실제로 표시된 간격을 보니 끊김이 `--fg-log`(OpenScaler가 화면을 낸 간격)보다 1.5~2배 많았다. 끊김을 "Present가 늦음"(자체 기록에도 잡힘)과 "Present는 제때인데 표시가 늦음"으로 나누면 절반쯤이 뒤쪽이고, 그 화면들은 PresentMon의 GPU 시간이 7~12ms였다. GPU 작업이 늦게 끝나 DWM 합성이 한 칸 뒤에 표시한 것으로 본다. 장면을 낸 뒤 표시까지는 실행마다 13ms 또는 20ms로 갈렸다 (합성 주기와의 위상).

- 확대 화면 창에서 `WS_EX_LAYERED`를 빼는 시험 옵션으로 합성을 건너뛸 수 있는지 보려 했지만, 레이어드가 아니면 클릭이 게임 창으로 전달되지 않았다 (3번 중 0번, 지금 방식은 3번 모두). 되돌렸다.
- README 144Hz 표의 끊김 열을 화면 기준(PresentMon)으로 다시 쟀다. DJMAX 블록 30~53번, 건반 영역 17번, 외삽 20번 / 마인크래프트 블록 20~60번, 영역 13~17번, 외삽 27~67번, RIFE+영역 383~420번 (분당). 이때 적은 "게임 46~52fps, 멈춤 14~24%"는 측정 스크립트 문제였다 (아래 "마인크래프트 144Hz 다시 재기").
- `tools/test/pmcompare.py`: PresentMon이 자정을 넘긴 시각을 시 한 자리로 적어 읽기를 고쳤다.

## 마인크래프트 144Hz 다시 재기, 30fps (2026-11-23, 1.3.11)

위에서 마인크래프트가 "46~52fps로 고르지 않고 멈춤 14~24%"로 나온 것은 측정 스크립트 문제였다.

- 원인: 측정 스크립트는 20초 동안 시점을 돌리고 멈추는데, OpenScaler는 `--duration`이 끝날 때까지 1~2초 더 기록한다. 그동안 마인크래프트 화면이 그대로라 새 게임 프레임이 없고, `fgtiming.py`가 이를 같은 장면 반복(멈춤)과 낮은 게임 fps로 셌다.
- 확인 방법:
  - PresentMon으로 보면 게임(javaw)은 초당 29.9장(최대 30일 때)을 고르게 냈다. OpenScaler 콘솔의 캡처 fps는 144였다 (WGC는 화면 합성마다 프레임을 주고, 같은 화면은 중복 검사가 버린다).
  - 받아들인 게임 프레임 사이 간격은 거의 모두 한 프레임(33ms)이었고, 끝 1.3~1.8초만 비어 있었다.
  - 지난 기록에서 마지막 새 프레임 뒤를 잘라 다시 매기니 게임 46~52fps → 57~59fps, 멈춤 14~24% → 대부분 0~4%였다.
- 화면 기준 끊김(PresentMon)은 시점을 돌린 구간만 잘라 세므로 영향이 없었다.
- 고친 방법: 측정 스크립트가 OpenScaler가 끝날 때까지 시점을 계속 돌린다. 30fps 기록은 끝 구간을 잘라 매겼다.

다시 잰 결과 (화면 기준 끊김은 분당, 각 묶음의 첫 실행은 시작 직후 GPU 시간이 튀어 분당 116~127번이라 뺐다):

| 방식 | 60fps (배수 2.4) | 30fps (배수 4.8) |
|---|---|---|
| 블록 매칭 보간 | 끊김 20~37번, 시간 고르기 0.11~0.12칸, 멈춤 0~0.1% | 끊김 30번, 0.35칸, 0.8% |
| 블록 매칭 + 영역 | 13번, 0.12~0.15칸, 0% | 13~17번, 0.10~1.19칸, 0.1~5% |
| 블록 매칭 외삽 | 23번, 0.26~0.71칸, 건너뜀 95~204번 | 23~27번, 0.35~0.66칸, 건너뜀 15~50번 |
| RIFE + 영역 | 363~400번, RIFE 제때 77~84%, 추가 지연 14~15ms | 600번, RIFE 제때 100%, 추가 지연 25ms |

- 30fps에서 RIFE는 결과를 모두 제때 냈지만, RIFE를 돌리는 화면의 GPU 시간이 중앙값 3.1ms, 90% 6.0ms라 144Hz 한 칸(6.9ms)을 자주 넘었다 (Present가 늦음 393번 + 표시만 늦음 207번). 60fps보다 신경망을 덜 돌리는데도 끊김이 많은 이유는 더 보지 못했다.
- 블록 매칭은 게임이 30fps여도 끊김이 60fps와 비슷했다.
