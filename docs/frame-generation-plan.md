# 프레임 생성 계획

블록 매칭 생성기, 학습 1, 2단계, RIFE 생성기를 구현했습니다. 학습 3단계(신경망 미세 조정)는 아직 없습니다. 실제 게임에서는 아직 확인하지 못했습니다.

## 사용자 요구

- 이 PC의 성능은 신경 쓰지 않는다. 테스트는 다른 기기에서 한다.
- 텀프로젝트이므로 한계가 있더라도 비교적 새로운 방식을 시도한다.
- 연결한 게임을 기록하고, 게임별 특징에 맞춰 프레임 생성 방식을 다르게 하며, 쓸수록 좋아지게 한다.
- 예: 리듬게임은 노트가 나오는 영역을 집중해서 부드럽게 만든다.

## 결정 사항

- 구현 범위: 옵션 B. 블록 매칭과 학습 1, 2단계를 먼저 완성한 뒤 RIFE 기반 생성기를 추가한다. 게임별 미세 조정은 일정이 남으면 진행한다.
- 테스트 기기 GPU: 아직 모른다. GPU 제조사에 묶이지 않게 만들고, 부담은 품질 설정으로 조절한다.
- 기본값: 배수는 주사율까지 자동, 방식은 보간, 움직임 격자는 1/4 해상도. 사용자가 따로 정하지 않아 제안값을 그대로 썼고 모두 설정에서 바꿀 수 있다.

## 구현한 파이프라인

`src/framegen.cpp`, `src/framegen_shaders.h` (D3D11 컴퓨트 셰이더)

진짜 프레임이 올 때:

1. 앞 프레임과 비교해 내용이 같으면 버린다. 캡처는 게임이 그리지 않아도 프레임을 보내기 때문이다 (30fps 창에서 초당 60번 온 것을 확인했다).
2. 휘도 피라미드를 만든다 (원본, 1/2, 1/4, 1/8, 1/16).
3. 두 방향(A->B, B->A)으로 블록 매칭을 한다. 1/16에서 전체 탐색하고, 후보(굵은 단계, 이전 프레임, 화면 지도)와 주변 탐색으로 세밀하게 내려간다. 그 자리에서 두 프레임이 같은 칸은 탐색 없이 움직임 0으로 둔다.
4. 후보가 모두 맞지 않는 칸은 1/8 영상에서 넓게 찾는다 (작고 빠른 물체용).
5. 양방향 결과가 서로 반대인지 검사해 신뢰도를 구한다.

화면을 그릴 때마다:

1. 표시 시계로 A와 B 사이의 시점 t를 구한다. 캡처 시각의 흔들림을 바로 따라가지 않도록 천천히 맞춘다.
2. 블록을 시점 t의 위치로 옮겨 적고(투영), 빈칸은 움직임이 작은 주변 벡터로 채운다. 벡터를 그대로 쓰지 않고 옮겨 적어야 작은 물체가 배경의 움직임에 묻히지 않는다.
3. 픽셀마다 주변 칸의 벡터와 "움직임 없음"을 후보로 놓고 두 프레임이 잘 맞는 후보에 비중을 준다. 한쪽에만 보이는 곳은 그쪽 색을 쓰고, 맞는 후보가 없으면 블렌딩한다.
4. 결과를 기존 업스케일에 넘긴다. 커서는 보간하지 않으므로 최신 위치로 그려진다.

게임이 주사율만큼 프레임을 내면 넣을 자리가 없으므로 그대로 보여 주고 지연도 늘리지 않는다.

## 게임별 학습

`src/game_profile.cpp`. 실행 파일 이름으로 게임을 구분하고 `profiles/게임이름.json`에 저장한다. 게임 화면은 저장하지 않는다.

| 단계 | 상태 | 내용 |
|---|---|---|
| 1. 설정 자동 조정 | 완료 | 1초마다 F0, F1, F2 중 F1을 가리고 현재 값과 후보 값으로 만들어 실제 F1과 비교한다. 6번 평균으로 후보가 더 좋으면 바꾼다. 3번마다 한 번은 기본값을 시험해 더 나으면 되돌린다. 대상: 칸 크기, 탐색 범위, 벌점, 허용치, 화면 지도 사용 여부 |
| 2. 화면 지도 | 완료 | 화면을 32x18칸으로 나눠 칸별 주된 움직임, 움직이는 비율, 고정 비율을 쌓는다. 움직임 후보로 쓰고, 일반/리듬게임/스크롤 유형을 판단한다 |
| 3. 신경망 미세 조정 | 미착수 | RIFE 생성기와 일정이 먼저 필요하다 |

화면 지도는 강제로 쓰면 점수가 떨어지는 장면이 있었다 (pan_ui). 그래서 채점에서 더 좋을 때만 켜지는 값으로 만들었다.

게임 유형(일반/리듬게임/스크롤)은 화면 통계로 계산만 하고 생성 방식을 바꾸지 않는다. 예전 설정의 "게임 유형"은 "일반"이면 화면 지도를 끄는 것뿐이고 "자동"과 "리듬게임"의 동작이 같아 사용자가 오해할 수 있었다. 그래서 설정을 "화면 지도: 자동 / 끔"으로 바꾸고, 설정 창에서 유형 표시를 뺐다. 예전 설정 파일의 리듬게임(2)은 자동으로 읽는다.

### DJMAX에서 학습 효과 확인 (2026-11-15)

`OpenScaler.exe --fg-gaptest 덤프폴더 출력폴더 프로필.json`으로, DJMAX 플레이 화면의 진짜 프레임에서 기본값과 학습된 설정을 비교했다. 각 설정에는 실시간과 같이 긴 간격 처리를 덧붙였다. 2칸은 학습 채점과 같은 조건이다. 녹화 두 개의 값 (dB):

| 프로필 | 학습된 값 | 2칸 기본 -> 학습 | 4칸 기본 -> 학습 | 6칸 기본 -> 학습 |
|---|---|---|---|---|
| 11/03 (루트 `profiles`, 사용자 실행) | 칸 4, 벌점 0.0040, 허용 0.14, 지도 안 씀. 채점 116회, 채택 4회 | 29.6 -> 26.4 / 29.6 -> 27.1 | 24.3 -> 24.5 / 25.2 -> 25.4 | 22.0 -> 22.1 / 23.2 -> 23.2 |
| 11/11 (`build\profiles`, 측정 실행) | 칸 16, 벌점 0.0015, 허용 0.14, 지도 사용. 채점 226회, 채택 9회 | 29.6 -> 29.2 / 29.6 -> 29.3 | 24.3 -> 26.3 / 25.2 -> 27.0 | 22.0 -> 23.0 / 23.2 -> 24.0 |

- 학습이 자기 채점 조건(2칸)에서 오히려 나빠졌다. 11/03 프로필은 2.5~3.2dB, 11/11 프로필은 0.3~0.4dB 내려갔다.
- 11/11 프로필은 긴 간격에서 좋아졌는데, 학습된 칸 16 때문이다 (긴 간격 처리는 칸을 8 이상으로만 키운다).
- 화면 지도만 켜면 11/11 프로필에서 2칸 +0.15~0.19dB로 작은 효과가 있었다. 11/03 프로필의 지도는 결과가 기본값과 소수점까지 같아 실제로 쓰이지 않은 것으로 보인다. 이유는 확인하지 못했다.
- 짐작되는 원인: 학습은 화면이 움직이기만 하면 곡 선택, 결과, 플레이 화면을 가리지 않고 채점하고, 후보를 6번 평균해 조금이라도 나으면 채택한다. 메뉴 화면에서 크게 좋아진 후보가 플레이 화면을 나쁘게 해도 채택될 수 있고, 채택한 값을 기본값과 다시 비교해 되돌리는 장치가 없다.

### 학습 재현과 규칙 수정

`--fg-gaptest`는 덤프의 앞 절반으로 실제 프로그램과 같은 순서로 360회 학습하고, 보지 않은 뒤 절반의 2칸에서 기본값과 비교한다 (`fg_gaptest_learning.csv`). 다른 화면이 섞인 경우는 게임 프레임과 계산으로 만든 장면을 24회씩 번갈아 채점해 흉내 낸다.

- 플레이 화면만으로 학습하면 세 녹화 모두 +0.2~0.6dB 좋아졌다. 학습 방식 자체보다 다른 화면이 섞이는 것이 문제다.
- 섞으면 재현됐다. pan_ui를 섞으면 벌점이 0.004로 올라 DJMAX에서 -1.46dB (11/03 프로필과 같은 값), fade를 섞으면 -0.45dB. 채택이 15~16회로 많아 화면이 바뀔 때마다 값이 오갔다.

세 가지 규칙을 녹화 세 개 x 섞은 장면 7가지(없음 포함) = 21경우에서 비교했다 (학습값 - 기본값):

| 규칙 | 평균 | 가장 나쁜 경우 | 기본값보다 나빠진 경우 | 계산 장면 학습 (자체 테스트) |
|---|---|---|---|---|
| 이전: 6번 평균 | +0.25dB | -1.46dB | 3번 | +1.2 ~ +13.1dB |
| 12번, 중앙값과 이긴 비율 2/3, 기본값 되돌림 | +0.12dB | -0.45dB | 7번 | +0.4 ~ +8.7dB (느려짐) |
| 적용: 6번 평균 + 기본값 되돌림 | +0.34dB | -0.60dB | 1번 | +1.3 ~ +13.2dB |

적용한 규칙: 후보 시험 3번마다 한 번은 기본값(지도 사용 여부는 그대로)을 후보로 시험한다. 기본값은 6번 중 중앙값이 0보다 크고 절반 이상 이기면 돌아간다. 칸이 작아지는 계산 부담 기준은 기본값으로 돌아갈 때는 적용하지 않는다. 다른 후보는 이전과 같이 평균으로 판단한다. 이미 저장된 프로필도 다음 실행부터 기본값과 다시 비교된다.

- 화면을 구분해 따로 학습하지는 않았다. 메뉴에서 오래 머문 뒤에는 여전히 메뉴에 맞는 값이 될 수 있고, 게임 화면으로 돌아오면 기본값 되돌림으로 회복하는 구조다.
- 실제 게임에서 다시 학습시켜 확인하지는 못했다. 위 수치는 녹화 프레임으로 재현한 것이다.

## 측정으로 확인한 한계

- rhythm 장면은 블렌딩보다 낫지만 22dB대로 낮다. 생김새가 같은 노트가 여럿이면 다른 노트와 짝지어 일부가 깨진다.
- fade 장면은 블렌딩보다 낮다. 밝기 변화를 움직임으로 착각하는 경우가 남아 있다. 학습으로 많이 줄지만 없어지지는 않는다. 평균 밝기 차이를 빼는 방법을 시도했으나 매끄러운 무늬에서 오히려 크게 나빠져 되돌렸다.
- 점수는 계산으로 만든 영상의 값이다. 게임에서의 품질과 체감은 아직 확인하지 못했다.
- 학습은 채점 때마다 움직임 추정을 2번 더 하므로 1초에 한 번 GPU 부담이 늘어난다.
- 학습은 블록 매칭의 값만 조정한다. RIFE를 쓰는 동안에도 채점은 돌지만 RIFE 자체는 좋아지지 않는다.
- RIFE는 지연이 신경망 시간만큼 더 늘어난다 (위 표에서 52ms -> 76ms). 프레임 간격의 70%를 넘으면 입력 해상도를 자동으로 낮추고, 낮춘 값은 그 실행 동안 유지한다.
- RIFE는 시점 0.5의 움직임 하나를 비례해서 다른 시점에 쓴다. 근사라서 t=0.25에서 sprites 점수가 내려간다 (53.38 -> 50.41).
- 입력 크기가 바뀔 때마다 신경망 세션을 다시 만들어 몇 초 동안 블록 매칭을 쓴다.

## 사용자에게 이미 설명한 한계

- 보간은 입력 지연을 늘린다. 30fps 게임이면 약 33ms + 계산 시간(추정치)이고, 학습으로 줄어들지 않는다.
- 게임 프레임이 모니터 주사율 이상이면 넣을 자리가 없다. 60Hz 모니터에서는 60fps 미만일 때만 효과가 있다.
- 게임의 움직임 정보 없이 화면만 보므로 가장자리, UI 주변, 빠른 움직임에서 깨짐이 생긴다.
- 오차 점수와 체감은 다르다. F0과 F2는 실제 보간보다 간격이 2배 넓어 근사치다.
- 1, 2단계의 향상에는 끝이 있다. 계속 좋아지는 효과는 3단계가 필요하다.
- 3단계는 게임 화면을 디스크에 저장한다. 용량 제한과 삭제 기능을 넣고 외부로 전송하지 않는다.
- 개발 계획의 마지막이 12월이라 일정이 빠듯하다.

## 프레임 간격이 고르지 않을 때

표시 시계는 최근 간격의 중앙값만큼 늦게 가는데, 짧은 간격의 쌍이 도착하면 시계가 아직 그 앞 쌍에 있다. 최신 쌍만 쓰던 때는 시점이 0에 묶여 멈췄다가 건너뛰었다 (DJMAX 게임 오버 화면에서 발견). 이제 한 쌍 앞의 움직임과 RIFE 결과도 보관해 시계가 있는 쌍을 보여 준다.

간격을 1, 2, 2칸으로 되풀이하는 시험 창 (GTX 1060, 60Hz, 측정 구간 약 330칸):

| 경우 | 화면 진행 표준편차 | 멈춤 | 33ms 넘게 건너뜀 |
|---|---|---|---|
| 블록 매칭, 고치기 전 | 10.9ms | 41 | 41 |
| 블록 매칭, 고친 뒤 | 4.9ms | 0 | 13 |
| RIFE, 고치기 전 | 10.8ms | 74 | 69 |
| RIFE, 고친 뒤 | 3.7ms | 0 | 0 |

RIFE는 고친 뒤에도 이 GPU에서 신경망이 20ms 걸려 짧은 간격의 쌍을 제때 못 맞추므로 합성의 약 3분의 2를 블록 매칭이 대신했다 (이후 "RIFE 속도" 절에서 개선). 게임 화면에서는 아직 확인하지 못했다. DJMAX 결과 화면은 간격이 대부분 1칸이라 이 상황이 거의 생기지 않았다 (아래 DJMAX 절).

## 슬로모션 테스트

120Hz 모니터 없이 프레임 생성 결과를 보려고 사용자가 제안한 방식이다. 짧게 녹화해 목표 fps만큼 채운 뒤 화면을 그릴 때마다 한 장씩 보여 준다 (60 x N장을 N초 동안).

- 처음 제안은 캡처를 초당 60회보다 많이 하는 것이었지만, Windows.Graphics.Capture는 화면 합성 주기에 묶인다. 수직동기 없이 초당 4,608번 그리는 창도 60Hz 모니터에서는 60fps로 캡처됐다. 그래서 받을 수 있는 프레임을 모두 받고 나머지를 생성으로 채운다. 주사율이 높은 모니터에서는 같은 코드가 그만큼 더 받는다.
- 프레임 쌍마다 나눌 수는 첫 프레임부터의 시간과 목표 fps로 정한다. 30fps 게임은 쌍마다 4등분, 60fps 게임은 2등분이 되고 프레임이 빠진 구간은 더 많이 나눈다.
- 방식이 외삽이면 실시간과 같이 다음 진짜 프레임을 쓰지 않는다. 앞의 진짜 프레임 두 장으로 움직임을 구해 다음 진짜 프레임 전까지를 예측하고, 블록 매칭으로만 만든다. 녹화 첫 쌍은 앞 프레임이 없어 진짜 프레임을 반복한다.
- 측정 (GTX 1060, 60Hz, 800x450, 초당 600픽셀로 움직이는 막대, 1초 녹화, 목표 120fps):

| 생성기 | 표시 프레임 (진짜 + 생성) | 건너뜀 | 재생 시간 | 프레임당 이동 중앙값 (이론값 5.00) | 표준편차 |
|---|---|---|---|---|---|
| 블록 매칭 | 120 (58 + 62) | 0 | 1.98초 | 5.00픽셀 | 0.20 |
| RIFE | 120 (59 + 61) | 0 | 1.97초 | 4.99픽셀 | 0.40 |

- 위 측정 때는 녹화 직후 간격이 33~50ms로 벌어져 1초에 진짜 프레임이 58~59장만 들어왔고, RIFE의 큰 깨짐도 그 구간에서 나왔다. 프레임을 담을 텍스처를 녹화 전에 미리 써 두고 처음 0.25초를 버리도록 고친 뒤 막대 창에서 진짜 60장 + 생성 60장이 됐다.
- DJMAX RESPECT V 플레이 구간(1280x720)은 60fps로 캡처되어 60Hz에서는 실시간 보간이 들어갈 자리가 없다. 슬로모션으로 본 노트 이동은 블록 매칭과 RIFE 모두 표시 프레임당 9.0픽셀로 진짜 프레임과 같았다. 블록 매칭은 노트가 고정 글자 위를 지날 때 글자가 끌려가는 잔상이 있다.
- 확인할 수 있는 것: 생성 프레임의 품질, 깨지는 위치, 목표 fps에서의 움직임. 확인할 수 없는 것: 실제 지연, 실시간 끊김, 그 GPU에서 제때 만드는지. 실제 게임에서의 체감은 아직 확인하지 못했다.

## DJMAX RESPECT V에서 확인 (2026-11-11)

조건: GTX 1060, 60Hz, 1280x720 창을 1920x1080으로 FSR 확대, 곡 "너랑 있으면" (BPM 130, 게임 오버가 나지 않는 난이도). 게임에는 Enter만 입력했다 (그 밖의 입력은 게임이 비정상 동작으로 보고 꺼질 수 있다).

- 확인하지 못한 것: 게임 오버 화면에서 불규칙 간격 수정의 효과, 실시간 RIFE와 외삽, 다른 곡, 체감.

## 긴 간격 (게임이 멈칫한 쌍)

DJMAX에서 진짜 프레임 사이가 2칸 이상 벌어지는 일이 대략 초당 한 번 있었고, 67ms 공백에서 블록 매칭이 깨졌다.

측정 방법: `OpenScaler.exe --fg-gaptest 덤프폴더 출력폴더`. 슬로모션 덤프의 60fps 진짜 프레임에서 k와 k+간격으로 가운데를 만들고, 건너뛴 진짜 프레임을 정답으로 비교한다. 실제 게임 화면으로 긴 간격의 품질을 숫자로 잴 수 있다.

원인 조사:

- 탐색 범위는 원인이 아니다. 4칸 동안 노트가 약 36픽셀 움직이는데, 가장 굵은 단계의 탐색은 192픽셀까지 본다.
- 앞 쌍의 움직임 힌트도 원인이 아니다. 힌트를 쓰든 안 쓰든 차이가 0.2dB 안이었다.
- 깨지는 곳은 내용이 바뀌는 곳이다. 제자리에서 밝기와 대비가 바뀌는 BREAK 글자, 판정선에서 사라지는 노트, 위에서 새로 들어오는 노트. 간격이 길수록 이 변화가 커져 작은 칸이 다른 물체와 맞는다.
- "움직임 없음" 후보를 밝기 변화에 덜 민감하게 비교해 보았다. 무늬 없는 곳까지 적용하면 롱노트 위아래에 반투명한 띠가 생겼고, 무늬 있는 곳에만 적용하면 효과가 없어(+0.02dB) 되돌렸다.
- 2칸에서 4칸이 되면 블록 매칭이 약 7dB 떨어지는데, 칸 크기를 키우고 벡터 차이 벌점을 낮추면 대부분 회복된다.

적용한 처리: 쌍의 간격이 최근 간격 중앙값의 2.5배를 넘으면 칸 크기를 8픽셀 이상, 벌점을 0.0004 이하로 쓴다. 이때는 앞 쌍의 움직임을 힌트로 쓰지 않고 화면 지도 표본도 뽑지 않는다. 실시간과 슬로모션(보간, 외삽) 모두 같다. 함께 고친 것: 실시간 추정과 화면 지도 표본이 쌍의 실제 간격 대신 중앙값을 써서, 긴 간격에서 화면 지도의 움직임 힌트가 1칸 분량으로 계산되던 문제.

DJMAX 녹화 두 개 (RIFE 녹화 / 블록 매칭 녹화의 진짜 프레임, 1280x720, dB):

| 간격 | 시점 | 멈춤 | 블렌딩 | 블록 (이전) | 블록 (긴 간격 처리) | RIFE |
|---|---|---|---|---|---|---|
| 2칸 | 0.5 | 20.6 / 21.4 | 22.7 / 23.7 | 29.6 / 29.6 | 같음 (보통 간격) | 30.5 / 30.5 |
| 3칸 | 1/3 | 20.6 / 21.4 | 21.6 / 22.6 | 25.5 / 25.9 | 27.4 / 27.9 | 27.5 / 28.1 |
| 4칸 | 0.5 | 18.4 / 19.4 | 20.2 / 21.2 | 22.2 / 23.2 | 24.3 / 25.2 | 26.4 / 27.4 |
| 4칸 | 0.25 | 20.5 / 21.4 | 21.4 / 22.4 | 24.3 / 25.1 | 26.3 / 27.0 | 25.1 / 26.5 |
| 6칸 | 0.5 | 17.7 / 18.6 | 19.6 / 20.6 | 21.0 / 21.7 | 22.0 / 23.2 | 22.6 / 24.1 |
| 8칸 | 0.5 | 17.1 / 18.1 | 18.9 / 20.1 | 19.6 / 20.6 | 20.9 / 22.0 | 19.4 / 21.4 |

자체 테스트의 계산 장면, 4칸 간격 (`fg_longgap.csv`, 1280x720, dB):

| 장면 | 블렌딩 | 기본 | 긴 간격 처리 |
|---|---|---|---|
| pan | 25.40 | 41.93 | 42.98 |
| pan_ui | 25.50 | 39.35 | 37.38 |
| sprites | 31.75 | 31.93 | 33.27 |

- 칸 16픽셀은 DJMAX 4칸에서 약 +3.5dB로 더 좋았지만, 움직이는 배경 위의 고정 UI(pan_ui)가 5dB 나빠져 8픽셀로 정했다. 8픽셀에서도 pan_ui는 2dB 내려간다.
- 벌점 0.0004가 빠른 이동에서 결정적이다 (fast_pan: 칸 8에 벌점 0.0008이면 15.8dB, 0.0004면 22.6dB).
- 보통 간격(2칸)에 같은 설정을 쓰면 오히려 내려가서 긴 간격에만 쓴다.
- 남은 문제: BREAK 글자처럼 제자리에서 밝기가 크게 바뀌는 글자는 여전히 찢어진다. 4칸 이상에서는 블록 매칭이 RIFE와 비슷해졌지만, 화면으로 보면 RIFE가 더 깨끗하다.
- 실시간 확인: 간격이 2, 4, 6칸으로 섞이는 시험 창에서 실시간 보간(블록 매칭, RIFE)과 슬로모션(보간, 외삽)이 정상 동작했다. 실시간 끊김 수치는 시험 창의 간격 분포가 실행마다 달라 비교하지 않았다. 실제 게임에서의 화면은 아직 확인하지 못했다.

준비:

기록 모으기 (약 5분, 파이썬 필요 없음):

```powershell
powershell -ExecutionPolicy Bypass -File tools\devicecheck.ps1 -Target "창 제목 일부" -Seconds 30
```

4. 화질 측정용 슬로모션 덤프 2초

- README 시연 GIF 다시 찍기: `tools/test/demoform.ps1` 창이나 실제 게임을 비교 모드로 확대하고 슬로모션을 한 장씩 넘기며 찍는다 (이 PC에서 쓴 방법). 영상 녹화가 된다면 실제 속도 영상도 남긴다.

## RIFE 생성기

`src/rife.cpp`, `tools/rife_export.py`

- 진짜 프레임 쌍마다 신경망을 별도 스레드에서 한 번 돌려 시점 0.5의 움직임과 마스크를 얻고, 합성은 원본 해상도에서 셰이더로 한다. 입력을 줄여도 화면이 흐려지지 않고, 표시 프레임마다 신경망을 돌리지 않아도 된다.
- 표시 시계를 신경망 시간만큼 더 늦추고, 새 결과가 나올 때까지 앞 프레임 쌍을 계속 보여 준다.
- 실행 파일 옆 `rife` 폴더(약 57MB)의 DLL과 모델을 실행 중에 불러온다. 폴더가 없거나 실패하면 블록 매칭을 쓴다 (폴더 없이 실행해 확인함). git에는 넣지 않고, 자동 빌드가 NuGet과 Hugging Face에서 받아 모델을 변환한 뒤 릴리스 zip에 넣는다 (`tools/rife_export.py`가 ONNX Runtime CPU 결과와 PyTorch 결과를 비교해 다르면 멈춘다).

## RIFE 속도

`OpenScaler.exe --rife-bench 폴더`로 입력 크기별 신경망 시간만 잰다 (16:9, 30번 중 처음 3번 제외, GTX 1060). 환경 변수 `OPENSCALER_RIFE_PROFILE`에 파일 이름 앞부분을 주면 ONNX Runtime의 연산별 기록(JSON)도 남는다.

| 입력 | 처음 | 크기 고정 | + 출력 복사 제거 |
|---|---|---|---|
| 256x128 | 14.7ms | 5.4ms | 4.9ms |
| 320x192 | 16.8ms | 8.6ms | 6.7ms |
| 448x256 (빠름) | 19.4ms | 12.8ms | 9.9ms |
| 704x384 (기본) | 32.0ms | 27.2ms | 21.8ms |
| 1024x576 (고품질) | 70.0ms | 55.7ms | 43.3ms |

- 크기 고정: 모델은 크기가 바뀌어도 되게 내보냈기 때문에 실행할 때마다 크기 계산 연산 39개가 CPU에서 돌고, DirectML이 연산 280개를 하나씩 실행했다. 가장 작은 입력도 14.7ms가 걸린 이유다. 세션은 원래 크기마다 새로 만들므로 `AddFreeDimensionOverrideByName`으로 크기를 정해 주니 크기 계산이 미리 끝나고 고정 비용이 사라졌다. 모델 파일은 바꾸지 않았다.
- 출력 복사 제거: 신경망 출력(평면 5장)을 미리 만든 버퍼에 바로 받고, 픽셀마다 다시 늘어놓지 않고 세로로 이은 텍스처 하나로 올린다. 버퍼는 돌려 받아 다시 쓴다. 신경망 실행 외의 시간이 2~7ms에서 0.1ms 아래로 줄었다.
- 자체 테스트의 RIFE 점수는 고치기 전과 같다 (1280x720 기본 품질 6개 장면이 소수 둘째 자리까지 같음).
- 크기를 바꿀 때: 너무 느려서 입력을 낮추면 새 세션을 만드는 몇 초 동안 RIFE가 멈춰 그동안 모두 블록 매칭으로 대신했다. 이제 새 세션을 뒤에서 만들고 그동안은 이전 크기로 계속 돌린다.
- GPU 선택: DirectML 장치를 0번 대신 성능 우선 GPU(`DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE`)로 고른다. 내장 GPU와 외장 GPU가 함께 있는 노트북을 위한 것이며, GPU가 하나인 이 PC에서는 차이를 확인할 수 없다.

실제 캡처 경로 (`tools/test/fgform.ps1` 시험 창 640x360 -> 1080p, 60Hz, 10초 중 앞 20% 제외, RIFE 기본 품질):

| 진짜 fps | 경우 | RIFE를 쓴 비율 | 신경망 | 마지막 입력 높이 | 지연 중앙값 |
|---|---|---|---|---|---|
| 21 | 고치기 전 | 85% | 22.8ms | (256으로 낮춤) | 74.4ms |
| 21 | 고친 뒤 | 100% | 23.8ms | 384 | 75.9ms |
| 32 | 고치기 전 | 64% (다른 실행 46%) | 21.5ms | (256으로 낮춤) | 56.6ms |
| 32 | 고친 뒤 | 98% (다른 실행 92%) | 9.8ms | 256 | 45.1ms |

- 21fps에서는 기본 입력 384를 낮추지 않고 그대로 쓴다. 32fps에서는 384(22ms)가 프레임 간격의 70%를 넘어 256으로 낮추지만, 256이 10ms라 지연도 11ms 줄었다.
- 60fps 게임(간격 16.7ms, 예산 11.7ms)이면 이 GPU에서는 256 또는 192까지 낮아진다. 이 PC는 60Hz라 60fps 게임은 애초에 보간할 자리가 없어 재지 못했다.
- 남은 방법: 모델을 다시 내보내 반정밀도(fp16)로 돌리기 (GTX 1060은 fp16이 느려 이 PC에서는 효과를 볼 수 없다), 가장 고운 단계(block4)를 빼서 계산 줄이기, 입력과 출력을 CPU를 거치지 않고 GPU에서 주고받기.
